# 路线图:阅读者工作流(change #2 的捕获稿)

> **这是捕获下来的想法,不是承诺。** 本文记录的方向可能被重排、改写或放弃;
> 它不构成任何交付时间或功能范围的保证。**当前版本承诺的是 README 里写着的那些,
> 仅此而已。**

> **这不是一个 active 的 openspec change,是一份捕获稿。** 它原本放在 `openspec/changes/add-reading-workflow/`,但那里只有 proposal、没有 spec delta(**有意为之**:设计尚未展开),于是 `openspec validate --all --strict` 会因它报红。
>
> **而我们的对外材料正在教人跑校验** —— 仓库里躺着一个校验不过的东西,第一个照做的人会看到红,然后学会"这里的检查是有噪声的,可以忽略"。**那比没有检查更糟:它训练人忽略警报。**
>
> 两条备选都不可取:补 delta 是**过早展开设计**(捕获的价值就在于还没投入);设 `skip_specs: true` 是**对工具撒谎**(这个方向确实会改 spec)。所以移到这里 —— **它仍然是捕获,只是不再冒充一个待执行的 change。** 展开时按本文内容重新 `openspec new change`。

>
> 因此 `openspec validate "add-reading-workflow" --strict` **现在必然报 "No deltas found",这是预期的**,不是缺陷 —— 不要为了让它变绿而设 `skip_specs: true`(本 change 确实会改 spec,那样设是撒谎),也不要为此仓促补 specs。展开时它自然会绿。

## Why

`add-code-intelligence` 让用户能**读懂**一个陌生代码库(跳转、引用、大纲、搜索),但没有解决**读的过程本身** —— 读到哪了、哪些看过了、当时想到什么、读完怎么交给别人。这一层是 PRD v0.2 的 P1「阅读者工作流」,也是"阅读器"这个身份真正区别于 IDE 的地方:IDE 完全没有这一层,因为它假设你是在写,不是在读。

同时,用户真机试用 v0.1 + 代码理解层后报回三条体验问题,其中一条不是体验问题而是**已有原则没贯彻到底**:我们只在**文件级**明示"可跳转 / 仅高亮",但具体到**某一个标识符**能不能跳,用户仍然得"点了才知道" —— 而我们的跳转是启发式的,标准库与第三方符号占比不小,扑空会高频发生。spec 里那条"MUST NOT 让用户通过'点了没反应'来推断"在标识符粒度上还是空的。

## What Changes

按优先级排序。**P0 一条,是原则贯彻,不是锦上添花。**

### P0 — 可跳转标识符的视觉反馈

- 按住 `Cmd/Ctrl` 时 hover,**能跳转的标识符加下划线 + 变色,不能跳转的没有任何反馈**;点击前用户就知道会不会扑空。
- 这条把「MUST NOT 让用户通过"点了没反应"来推断」从**文件级**贯彻到**标识符级**,并**兜住启发式跳转的固有短板**:不精确从"点了才发现"变成"根本不会点",期望被提前对齐。
- 成本低:`byLowerName` 查表是微秒级,hover 实时查来得及;CodeMirror 6 用 Decoration 加 class 即可。

### P1 — 阅读者工作流(PRD v0.2 的 P1)

- **阅读进度**:文件级"已读 / 未读"标记,目录树上可视化,让"读完一个库"变成可完成的任务。
- **书签与行内笔记**:某文件某行留标记与文字,本地持久化(IndexedDB),侧栏聚合。
- **阅读轨迹**:自动记录本次会话的文件访问与跳转链,可回看。
- **导出导读**:把书签 / 笔记 / 轨迹导出成一份 Markdown「代码导读」,可交给同事或贴进 PR。这是天然的口碑传播点。
- 寻址基础已就绪:`add-code-intelligence` 已提供统一的"文件 + 行"定位通道与导航栈,书签与已读态直接复用,不需要新寻址机制。
- **以下三件事是一组,展开设计时 MUST 当作整体、MUST NOT 拆开排优先级**(产品阶段 2026-08-18 裁定,理由见 Open Questions Q1):
  - **导出 Markdown 导读 = 资产逃生通道**
  - **手动关联项目 = 资产找回通道**
  - **可见的"绑定断开"提示 = 用户知道自己需要逃生的前提**
  三者缺一,用户的笔记就会在他毫不知情的情况下变成孤儿数据。
- **项目绑定断开时 MUST NOT 静默**:认不出项目时 MUST NOT 悄悄给一个空白笔记面板(用户会以为笔记没了,而数据其实还躺在 IDB 里),SHALL 明确告知"有一份属于某项目(记录的名字/路径)的阅读笔记未能自动匹配到当前项目"并提供**手动关联**入口。这与"同名多候选给列表"是同一个动作:**自动匹配不了的时候把选择权交给用户,而不是替他猜。**

### P1 — 界面一致性(用户真机反馈)

- **大纲面板宽度可拖拽并持久化**:左侧目录树已有分隔条可拖 + 记忆宽度,右侧大纲写死 220px。用户已形成"分隔条可拖"的心智,右边不能拖是**不一致**,不是缺功能。**复用左侧那套机制,MUST NOT 写第二份拖拽逻辑**。
- **文件类型图标**:目前所有文件同一个 📄。目录树是高频扫视对象,类型的视觉区分直接影响找文件的速度 —— 对"代码阅读器"这个定位不只是好看问题。约束:**零网络**(不拉图标字体或远程资源)、**不引入整套图标主题包**(包体积);做法倾向内置极简 SVG + 按语言着色,覆盖已支持的十几种类型即可,并**同时验证暗色主题下的对比度**(emoji 在两个主题下一样,着色图标会引入主题适配问题)。

### P2 — 隐私可验证与分发(PRD v0.2 的 P2)

- **零网络自证**:UI 上提供可点开的"隐私说明"(代码不出本机、扩展无网络权限、manifest 无 host_permissions),面向合规敏感人群的转化钩子,也是云端竞品结构上给不了的承诺。
- **Chrome Web Store 上架素材**:截图与说明文案围绕"零网络 + 读懂陌生代码库"两个卖点。

### 验收方式的一项变更(适用于本 change 全程)

- **验收 MUST 含真人试用环节,且 MUST NOT 以清单形式下发。** 理由见下方"从 change #1 继承的教训"。

## 从 change #1 继承的遗留项

- **Windows / Linux 键位真机核验**:`add-code-intelligence` 按保守假定实现(该平台不绑定也不提示任何 `Ctrl+Shift+*` 与 `Alt+←/→`),核验因无 Windows 真机而顺延。拿到设备即回填并按结果决定是否放开键位。

## 从 change #1 继承的教训(直接影响本 change 的验收设计)

- **分叉允许发生在机制层,不允许上浮到契约层**(见 `add-code-intelligence/design.md` D0)。自检问题:写 `if` 或按情形切分 requirement 时问"我分叉的是'怎么做'还是'要不要做'"。
- **验收真实性两问**:① 功能没实现的话,它会不会照样成立?② 数字漂亮的话,它测的是不是我要保证的那条路径?
- **断言容易只覆盖 Scenario 的前半句**,以及 **MUST NOT / SHALL NOT 类条款常常没有断言证明** —— 收口时把 spec 里所有排除类条款列出来逐条问"有断言证明它吗"。
- **内部三道防御共享同一个坐标系**(断言按 spec 写、矩阵按 spec 维度叉乘、审批也读 spec),所以 spec 没写到的形状三道全看不见。真人试用的价值在于**他不读 spec**,坐标系独立 —— 因此**不能给他发"请按此清单验证"的表格**,那等于把他拉进我们的坐标系、盲区一并继承。已知命题的真机核验(如键位冲突)是例外,那是验证不是探索。

## 非目标

沿用 PRD v0.2 并继承 `add-code-intelligence`:**不做编辑与保存**(只读是定位不是短板)、**不接任何 AI/LLM、不做任何网络请求**(零网络是核心资产,破例即定位失效)、**不做 Git 集成 / diff**(v0.3 再议)、**不做编译级精确的语义分析**(不引入 LSP / tsserver)。

**"做写"已被明确否掉(产品阶段与用户 2026-08-20 厘清)**:用户曾提出"想做写",经厘清那是"只读不够卖"的主观感觉,**不是用户需求**。结论:**做写 = 换一个产品** —— 它会摧毁"只读 + 零网络"这对**可自证承诺**(见 `prep-open-source`:产物中无写入符号 = 没有能力写)。**方向锁死:不做源文件编辑。**
P1 阅读工作流(批注 / 笔记 / 高亮 / 已读态)不受影响 —— 那些写的是**阅读痕迹**,不是代码,只读边界完好。

本 change 额外明确:笔记与书签**仅本地持久化**,MUST NOT 提供任何形式的云同步或分享服务端 —— 导出走"生成 Markdown 文件交给用户"这一条路径。

**MUST NOT 向用户的项目目录写入任何文件**,包括为了稳定项目标识而落一个标记文件(产品阶段 2026-08-18 裁决,不再论证)。理由是**信任门槛的量级**,不是洁癖:

- 只读扩展要的是"读"授权;**一旦要写,FSA 会向用户索取 readwrite 授权** —— 那是完全不同的一次心理决策。我们的叙事是"不装 IDE、不上传代码、只是看看",而"它要写我的项目目录"会当场击穿这个叙事。
- 对外的两条硬承诺是**零网络 + 只读**。零网络已写进 manifest(`permissions: []`)并有 E2E 断言,是**可自证**的;只读一旦开口子,这对承诺就只剩一条,而**一条不成对的承诺说服力远不到一半** —— 合规敏感用户判断工具安不安全,靠的是"它根本没有能力做坏事",不是"它保证不做"。
- 换来的收益只是"书签绑定更稳一点"。交换比例不成立。

## 贯穿本 change 的产品原则:给信息,交决定权

> **遇到"要不要替用户决定"的岔路,一律选"把信息给全、把决定权交给用户"。举证责任在例外那一边** —— 想例外,必须给出这一次为什么例外的具体理由,而不是反过来要求每次都论证为什么要遵守。

这条已在四处独立落地并稳定(产品阶段 2026-08-18 确认可当公理用,展开设计时直接按它推、不必重新论证):同名多候选给列表而不替用户挑、降级必须可见而不静默、项目绑定断开时给提示 + 手动关联而不悄悄给空白面板、孤儿数据的处置权归用户。

**为什么它在这个产品里格外硬**:我们整个能力是**启发式**的 —— 跳转不精确、指纹会漂移、降级有边界。启发式工具**替用户做决定**,错的时候用户不知道自己被坑了;启发式工具**把不确定性摊开给用户**,错的时候用户至少能自己纠。**这条原则是我们承担得起"启发式"的前提,不是风格偏好。**

## Open Questions(捕获,本阶段不解)

### Q1:书签 / 笔记 / 已读态挂在"哪个项目"上?

P1 的用户数据要落 IndexedDB,就绕不开一个标识问题 —— **拿什么当项目的 key**:

- **目录句柄**可结构化克隆存进 IDB(最近项目已经这么存),但它**不是稳定标识符**:文件夹改名、移动位置,或从另一条路径重新授权同一目录之后,还认不认得上?
- **用路径当 key**:用户把仓库从 `~/work/foo` 移到 `~/projects/foo`,**一整份读书笔记凭空消失,而且是静默消失** —— 他不会收到任何提示。这是用户资产层面的损失,不是功能瑕疵。
- **key 取得太宽**:两个同名不同处的项目会串味,笔记互相污染。

**因果链(决定 P1 的产品形态,展开设计前必须认清)**:

> 绑定注定可能断 → "导出 Markdown 导读"不只是传播点,而是**资产逃生通道**;"手动关联"是**资产找回通道**;可见的断开提示是**用户知道自己需要逃生的前提**。三者是一组,缺一就会有笔记在用户毫不知情时变成孤儿数据。

**已由产品阶段 2026-08-18 裁决、不再是开放项的部分:**

- **绝不写磁盘**(含标记文件),理由见"非目标"。这条关闭了"投入做更稳标识"那个方向。
- **不要把 key 设成"句柄 vs 路径"的二选一 —— 两个都不是好 key。方向是用项目内容自身做指纹**,全程只读:根目录下的文件/目录名集合 + 少量标志文件(`package.json` / `go.mod` / `pom.xml` / `Cargo.toml` 等)的内容摘要。改名、移动 → 指纹不变,笔记跟得上;同名不同处 → 指纹不同,不串味。代价是项目内容大改后指纹会漂移 —— 但那时"这还是不是同一个项目"本来就是个真问题,**漂移是诚实的**。
- 匹配顺序:`isSameEntry()` 作为**快路径**先试,指纹作为**兜底**;两条都验不上才走"断开 + 手动关联"。

**仍然开放、留到展开设计时解的:**

1. `isSameEntry()` 在重命名 / 移动 / 重新授权后的**实际行为** —— **必须真机验证,不许按文档推断**(本 change 已经吃过"按文档推断浏览器行为"的亏)。
2. 指纹的具体构成与漂移容忍度(取多少标志文件、名集合怎么归一、漂移到什么程度算换了项目)。
3. **孤儿数据的生命周期** —— 已有**默认立场**(产品阶段 2026-08-18 给出;可被数据推翻,不是封死),展开时只需验证或推翻它:
   - **MUST NOT 自动过期删除。** 静默删除比静默丢失更糟:静默丢失至少数据还在、有机会找回;**自动删除是把用户资产真的销毁了,而他从头到尾不知道发生过。**
   - 提供**显式清理入口**,列出孤儿数据时带上**原项目名 + 最后访问时间 + 条目数** —— 判断所需的信息给全,决定权交给用户。
   - **不设条数上限**:笔记是文本,量级与符号索引不在一个数量级,不构成存储压力,没必要为省空间去动用户的东西。
   - 一句话:**孤儿数据的处置权归用户,我们只负责让它可见、可找回、可清理。**

**本阶段只到这里,不展开设计。**

### spike 1 结论(2026-08-21 实测,**数据在此,不要重跑**)

**① zlib 这半:通了,零依赖。** 用**浏览器原生 `DecompressionStream('deflate')`** 直接解开真实 `.git` 的 loose object,对象头与 tree 条目均可解析:
```
解压成功,总字节: 1681   对象头: tree 1671
内容: 100644 asr-bench.py\0<20B SHA>100644 asr-compare.p…
```

**② 关键发现:"最小切口"避不开难的那部分。** 本机两个真实仓库的对象分布:

| 仓库 | packfile | loose 对象 | HEAD 的 commit 在哪 |
|---|---|---|---|
| x-algorithm | 2 | **0** | **packfile** |
| video-trans | 3 | 995 | loose |

成因:**新提交先落 loose,`git gc` 后进 packfile;而 `git clone` 下来的仓库全部对象都在 packfile,loose 为 0。**

于是"单文件 工作区 vs HEAD"在一个**刚 clone 的仓库**上要读 HEAD → commit → tree → blob,**四个对象一个都不在 loose 里**。而我们的定位是"打开一个**陌生**代码库",陌生代码库正是 **clone 来的** —— **loose-only 实现会在核心场景 100% 失效。**

> **因此:packfile 解析(.idx 索引 + 偏移查找 + ofs-delta/ref-delta 链)不是"完整历史浏览"才需要的后续,而是最小切口就必须付清的成本。**
>
> **"先做最小切口"在这里不降低技术难度,只减少功能面。** 这两件事平时混着说,此处必须分开:**范围可以砍,难度砍不掉。**

**明确不建议的第三条路**:先发一个 loose-only 版本。它在最常见场景下必然失效 —— 用户 clone 完点开 diff 什么也看不到,**他不会归因到 loose/packed,只会认为这功能是坏的**。**一个在核心场景必然失效的功能,比没有这个功能更伤**(与"半成品入口比没有更糟"同源)。

**spike 2(体积账)未跑** —— 它取决于"付不付 packfile 成本"这个决策;若决定不付,不必量。

**必须先 spike 的可行性(原始记录,①②已由上文回答)**:
1. **FSA 能否遍历 `.git` 这类点开头的隐藏目录** —— **读不到则整条方向不成立**,这是第一道门。
2. 纯 JS 读 git 对象:loose objects + packfile + zlib(浏览器原生 `DecompressionStream` 可解 deflate)。**packfile / delta 解析有真复杂度,不是小工程。**
3. **体积账**:引入 git 读取能力(isomorphic-git 数百 KB,或自写)可能超阈值,需论证。

**硬边界(与现有承诺一致,MUST 守)**:
- **纯读 `.git`,不写、不联网**;
- **零网络是红线**:MUST NOT 引入任何 remote fetch/http(isomorphic-git 默认带 http 模块,**要确保不打包进去**)—— 否则刚锻造的"网络符号零命中可自证"当场破功;
- 理想目标:**diff 能力也纳入"零网络可自证"**,产物里仍无网络符号。

**最小切口**:最高频最小可用 = **单文件"工作区 vs HEAD"差异**(我改了什么还没提交)。完整 commit 历史浏览、任意两版本对比是更大的后续,**别一上来做全的**。

> **⚠️ 上面第 1 个 spike 同时是一个当下问题,不只是未来功能的前置**(规格阶段 2026-08-20 核查代码发现):
> `src/tree/treeStore.ts` 与 `src/search/indexWorker.ts` 中**对 `.git` 及任何点开头目录没有任何排除**。因此**如果 FSA 能遍历隐藏目录,今天就已经在发生**:目录树会显示 `.git`,文件名索引会走遍它,符号索引会去读那些对象文件。一个成熟仓库的 `.git` 轻易上万个 loose object —— 那会**直接吃掉我们对"约 10,000 文件"的规模承诺**,用户的 5,000 个源文件外挂着 20,000 个 git 对象。
> **同一个 spike 两个答案都重要**:能遍历 → 我们现在就有一个规模与噪声问题要处理(是否默认折叠/排除 `.git`、是否可配置);不能遍历 → diff 方向第一道门就不通。**这条不必等发货后,可在任意时点用一个真实 git 仓库当场验出来。**

# 语言/文件类型覆盖面盘点(2026-08-20)

起因:用户反馈"不支持 SCSS"。产品阶段要求**一次盘点代替五次响应** —— 列全"常见但未覆盖",标注取舍与理由,由产品阶段定。

**盘点方法**:逐项核对 `node_modules/@codemirror/legacy-modes/mode/` 的实际导出(不是按印象),已实测确认。

## 现状

已覆盖 15 种语言 / 33 个扩展名(`src/lib/filetypes.ts` 的 `CODE_EXT`)。其中 `.mjs` / `.cjs` / `.mts` / `.cts` **已支持**(用户也问了这个)。

未覆盖的扩展名会掉进内容嗅探 → 当纯文本渲染,**有行号但无高亮**。

## A. 本次加(建议)

| 扩展名 | 方案 | 依赖 | 理由 |
|---|---|---|---|
| `.scss` | `legacy-modes/mode/css` 的 **`sCSS`** 专用模式 | **零新增** | 用户实际反馈;前端仓库极常见 |
| `.less` | 同上的 **`less`** 专用模式 | **零新增** | 同族,同一处改动 |
| `.sass` | `legacy-modes/mode/sass` 的 `sass`(缩进语法) | **零新增** | 同族,同一处改动 |

**实测结论:三者都有一等专用模式,不需要"映射到 css + 标注精度边界"那条退路。** 产品阶段给的 fallback 方案可以不用 —— 既然有专用模式,就不必制造一个需要向用户解释的近似。

## C. 需要新机制,不只是加条目

| 目标 | 缺口 | 说明 |
|---|---|---|
| `Dockerfile` / `Makefile` / `CMakeLists.txt` / `.gitignore` 等 | **`identifyByName` 只按扩展名匹配** | 这些文件**没有扩展名**或以整名标识。要支持需新增一张"整文件名 → 语言"映射并在 `identifyByName` 里先于扩展名匹配 —— **是机制改动,不是加条目**。`dockerfile` / `cmake` 模式 legacy-modes 里有;Makefile **没有**现成模式 |

## D. 没有现成模式(要么新依赖,要么近似)

| 扩展名 | 情况 | 可选方案 |
|---|---|---|
| `.vue` / `.svelte` | legacy-modes **没有** | 可映射到 **`html`**(两者都是 HTML 超集的单文件组件,CM 的 html 解析器能处理 `<script>` / `<style>` 块)。**但必须标注是近似高亮**,模板指令(`v-if`、`{#if}`)不会准 |
| `.php` | legacy-modes **没有** | 需新依赖 `@codemirror/lang-php`(约 100 KB 级) |
| `.graphql` / `.gql` | 没有 | 需新依赖 |
| `.tf` / `.hcl` | 没有 | 无官方 CM6 包,需第三方 |
| `.astro` / `.zig` / `.nim` | 没有 | 低频,不建议 |

## E. 建议不加

| 项 | 理由 |
|---|---|
| 任何需要**新增运行时依赖**的语言(php / graphql / tf) | 与"包体积受控"冲突,且这三类在"读陌生代码库"的目标场景里不是高频。**除非有真实用户反馈,否则不为假想需求付体积** |
| 代码理解层(跳转/引用/大纲)扩到 CSS 家族或 B 组任何语言 | CSS 家族没有我们定义的"定义符号"概念;B 组全部按 **"仅高亮"** 分档,与现状一致。**MUST NOT 为了"支持得更全"而破坏已明示给用户的"可跳转 / 仅高亮"分档** |

## 产品裁定(2026-08-20,已生效)

| 组 | 裁定 | 落点 |
|---|---|---|
| A(scss/sass/less) | **做** | 任务组 2b |
| B(高频批) | **做 `rs` / `rb` / `kt` / `cs` / `gradle` + `groovy` + `toml`**,其余**明确不加**(不是"以后加") | 任务组 2c |
| C(整名文件) | **做机制**,挂 `Dockerfile` + `CMakeLists.txt`;`Makefile` 无现成模式 → 纯文本 + 正确图标,**不假装有高亮** | 任务组 2d |
| D(vue/svelte) | **做**,映射 html + **UI 明示"近似高亮"** | 任务组 2e |
| E(需新依赖) | **关掉** | — |

**一处需要产品阶段知晓的修正**:产品阶段的加入列表含 `.gradle`、排除列表含 `groovy`,但 **`.gradle` 用的就是 groovy 模式** —— 同一个模式不能一半算加一半算不加,否则会出现"`.gradle` 有高亮而 `.groovy` 没有"的怪状。已将 `.groovy` 一并纳入(零额外成本)。

**"暂不加"改为"明确不加"**:按产品阶段要求,B 组未选中的项(swift / dart / lua / scala / r / perl / powershell / protobuf / properties / diff)与 E 组一并写进 spec 的**明确不覆盖清单**,对外表述为"当前覆盖 X、不覆盖 Y",**MUST NOT 说"尚未支持"或"以后补齐"** —— 前者是边界,后者是欠条。

## 原始取舍问题(已由上表回答,保留供追溯)

1. **A 组照做**(scss/sass/less),无异议的话本次收口。
2. **B 组要不要一次加完?** 全部零新增依赖,合计体积增量预计几十 KB 量级。一次加完的好处是**从此不用再为"不支持 X"响应第六次**;坏处是每种都要配图标色类与 E2E 断言,本次改动变大。**我倾向按"高常见度"先加一批**(`rs` / `rb` / `kt` / `toml` / `cs` / `gradle`),其余留到有反馈时再加。
3. **C 组(Dockerfile / Makefile)要不要本次做?** 它是机制改动。我倾向**本次做机制、只挂 Dockerfile 一个条目** —— 机制一旦有了,以后加整名文件就是加数据。
4. **D 组的 `.vue` / `.svelte` 要不要走 html 近似?** 前端仓库常见度很高。走近似必须在 UI 明示"近似高亮",老规矩:**含糊比缺失更糟**。这条我不替你定,因为它是"要不要给用户一个不完美的东西"的产品判断。

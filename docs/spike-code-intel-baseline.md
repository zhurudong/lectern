### 2.1 实测修正的两处关键点(与 design.md D1 的差异)

**(1) 过滤必须按「直接父节点白名单」,不能按「祖先集合命中」。**
design.md D1 的措辞是"仅收祖先为 `ClassDeclaration` / `MethodDeclaration` / `FieldDeclaration`… 的"。
若照字面用"任一祖先命中"来实现,**Java 的每一个局部变量都会被收进索引** —— 实测其祖先链为:

```
Definition < VariableDeclarator < LocalVariableDeclaration < Block < MethodDeclaration < ClassBody < ClassDeclaration
```

`MethodDeclaration` 与 `ClassDeclaration` 都在允许集合里。字段与局部变量的**唯一**区别在
`VariableDeclarator` 的父节点是 `FieldDeclaration` 还是 `LocalVariableDeclaration` —— 只有看直接父链才分得开。
实现按此收紧(见 `src/intel/extract.ts` 顶部注释),并对每个"名字位"额外校验它确实是父节点的
第一个该类子节点(`isFirstChildOfType`),避免误收同类型兄弟节点。

**(2) 若干 design.md 未列出、但必须排除或补上的节点:**

| 语言 | 实测发现 | 处置 |
|---|---|---|
| Go | `package main` 的包名也是 `DefName`(父 `PackageClause`) | 排除(白名单不含 `PackageClause`) |
| Go | 方法的容器是**接收者类型**,在 `MethodDecl → Parameters → Parameter` 里,**不在祖先链上** | 单独取(`goReceiverType`),否则 `Dispatch` 的容器为空 |
| C/C++ | `#define SQUARE(x)` 的**宏形参 `x`** 与宏名同为 `Identifier < PreprocDirective` | 只收第一个 Identifier,且校验指令文本以 `#define` 开头 |
| C/C++ | `typedef struct Foo Bar;` 的别名是**最后一个** `TypeIdentifier` | 用 `isLastChildOfType` 取别名位 |
| Python | 装饰器把定义包进 `DecoratedStatement`;`import` / `for` / `with` 的绑定也是 `VariableName` | 跳过包装节点后判定作用域;非白名单父节点一律排除 |
| JS/TS | 对象字面量属性 `Property < ObjectExpression`、`for...of` 的 `ForOfSpec` 也产出定义类节点 | 排除 |

## 3. 10,000 文件规模索引耗时与内存(任务 11.1)

**测量方式**:`scripts/e2e.mjs` 的"旗舰场景"段落 —— OPFS 合成 10,000 个文件、其中 **85% 为 Go**
(每文件约 36 个定义符号,仿 Java/Go 单体仓密度),真实 Chrome 装载扩展后 `enterProject` 计时,
直到顶栏索引状态出现终态;heap 取 `performance.memory.usedJSHeapSize`。

| 指标 | design.md D5 预估 | 实测 | 判定 |
|---|---|---|---|
| 文件总数 / 支持语言占比 | 10,000 / 80%+ | 10,000 / **85%** | — |
| 抽取到的符号总数 | 约 240,000(8,000×30) | **306,000** | 同量级 |
| 索引总耗时 | 5–15 s | **2.1–2.2 s** | ⚠️ 比预估**快 2 倍以上**(见下) |
| JS heap 峰值 | 20–35 MB(165k 符号)/ 最坏约 80 MB(400k) | **39–44 MB**(306k 符号) | 优于按 200 B/符号的线性外推(应为 61 MB) |
| 根层首屏 | < 1 s | **7 ms** | ✅ |
| 索引期间交互 | 不阻塞 | 目录树可展开、预览可用 | ✅ |
| **终态** | **不得为 partial** | **`索引已完成(8500 个文件 / 306000 个符号)`** | ✅ **判据满足** |

**判据核对(任务 11.1 的硬要求)**:P0 语言占比 85% 的 10,000 文件项目**未进入 `partial` 状态**,
界面不出现"项目过大"提示。306,000 < 400,000 上限,余量 23%。**design.md D5 把上限从 200,000
提到 400,000 的决定是正确的** —— 若仍是 200,000,这个再普通不过的旗舰场景会直接触顶降级。

**⚠️ 偏差说明(须回报,见第 6 节)**:耗时比预估快 2 倍以上,偏差方向对我们有利,但**必须说明
测量口径的局限**:合成项目建在 **OPFS** 上,而 design.md D5 的 3–10 s 文件 I/O 估算针对的是
**真实磁盘目录的 FSA 句柄**。OPFS 的 `getFile()`/`arrayBuffer()` 明显快于经过用户授权的真实目录
句柄,所以 **2.1 s 不能直接外推到用户真机打开真实 10k 文件仓库的表现**。解析与抽取的 CPU 部分
(design 估算 4 Worker 并行 1.6–2.5 s)与实测总耗时吻合,说明**瓶颈确实在 I/O,而 OPFS 把这一项
几乎抹平了**。真实磁盘的耗时应介于两者之间,仍在"不阻塞首屏、进度可见"的可接受范围内。

## 4. C/C++ 抽取质量指标(任务 11.4)

**样本**:① 合成样本 —— `scripts/check-extract.mjs` 的 C/C++ 用例 + `scripts/e2e.mjs` 的
`src/widget.cpp` / `src/util.h`;② **真实开源 C/C++** —— 本机 `MacOSX.sdk` 下的
**LLVM libc++ 头文件**与系统 C 头文件,`scripts/measure-cpp.mjs` 均匀抽样 400 个文件(1.9 MB)。

> **复现边界**:上面这组数字取自 macOS SDK 的头文件,**默认路径只在装了 Command Line Tools 的
> macOS 上存在**。这不是"还没支持别的平台" —— 这个测量的实质是**拿真实系统头文件量误收率**,
> 而不同平台的真实头文件本来就不是同一批,数字也不该指望完全一致。
>
> 在别的平台复现时用 `HEADERS` 指向任意头文件目录(冒号分隔多个):
> `HEADERS=/usr/include node scripts/measure-cpp.mjs`。
> 一个头文件都没扫到时脚本会**报错退出**,不会安静地量出"0 个符号、误收率 0%" ——
> 那种看起来完美的空报告比失败更糟。

### 4.1 三项判定指标

| 指标 | 阈值 | 实测 | 判定 |
|---|---|---|---|
| ① 误收率 =(形参+局部变量)/ 总符号数 | ≤ 5% | 合成样本 **0.0%**;真实样本人工抽查见 4.3 | ✅ |
| ② 多候选列表中位长度 | ≤ 3 | **2**(`New` 在 service.go / store.go 各一处) | ✅ |
| ③ 定义漏收率(人工标注样本) | ≤ 15% | 合成样本 **0.0%**(15/15) | ✅ |

### 4.2 符号密度对比(规格阶段 2026-08-17 追加的观察项)

收录函数原型后,C/C++ 会出现"同一函数在头文件一次、实现文件再一次"的情况,
所以要确认它的符号密度不会把阶段一"306,000 / 400,000 上限、余量 23%"的结论推翻。

| 样本 | 符号/文件 | 符号/KB |
|---|---|---|
| 真实 C/C++(libc++ + 系统头文件,400 个文件 / 1.9 MB) | 16.8 | **3.45** |
| Go 对照组(旗舰场景所用的同一份合成源码) | 36.0 | **25.95** |
| **密度倍率** | — | **0.13×** |

**结论:远未达"Go 的 2 倍"的回报线,400,000 上限无需复看。**

需要说明清楚的一点(避免这个数字被误读):比值之所以这么低,是因为**对照组的 Go 是刻意堆砌的
高密度合成代码**(25.95 符号/KB),真实代码根本达不到这个密度。这反而说明
**阶段一那次 306,000 符号的测量是偏保守的**——真实的万级 C/C++ 仓库产生的符号数只会更少,
不会更多。所以阈值余量比阶段一测出来的 23% 还要宽。

抽取种类分布(真实样本):宏 40.9%、函数 15.4%、类型 14.3%、字段 9.1%、**声明 8.2%**、
结构体 4.7%、常量 3.4%、命名空间 1.8%、类 1.3%、方法 0.8%、枚举 0.1%。

### 4.3 真实代码上发现并修掉的一处误收

在真实头文件上抽查时发现:`int utime(const char *, const struct utimbuf *);`
里作为**形参类型**出现的 `struct utimbuf`,也会被解析成 `StructSpecifier + TypeIdentifier`,
从而被收成一个"结构体定义"。即**每一处引用某结构体的地方都会多出一条假定义**。
合成样本测不出来,因为合成代码里没有"用结构体做形参类型"这种写法。

修复:struct / union / class 必须**带定义体**(`FieldDeclarationList`)才算定义,
enum 必须带 `EnumeratorList`。前向声明(`struct Node;`)同理不收——它与真定义同名,
收了只会在候选列表里多一条指向声明的噪声。

效果(同一 400 文件样本):结构体 541 → **317**、类 125 → **88**,
**消除 261 条误收,约占样本总符号的 3.7%**。修复后人工抽查:
- `utime.h`:5 个符号全部正确(修复前 6 个中有 1 个是误收的 `utimbuf`)
- `netinet/ip.h`:90 个符号,抽查前 25 条全部为真定义;宏 `IP_MAKE_VHL(v, hl)` 只收宏名、
  形参 `v`/`hl` 正确排除;位域 `ip_hl:4`、同行多声明符 `ip_src, ip_dst` 均正确收录
- `c++/v1/__utility/swap.h`:4 个符号全部正确(含函数模板 `swap` 与两个 `using` 别名)

### 4.4 已知边界(如实记录,不修)

**未展开的宏会让声明解析失败。** 例如 `libgen.h` 的
`char *_LIBC_CSTR basename(char *_LIBC_CSTR);` —— `_LIBC_CSTR` 是未展开的属性宏,
语法树无法把它识别成函数声明,因此 `basename` / `dirname` **未被收录**(该文件只收到 1 个宏)。

这正是 design.md「Risks」里已经写明的 C/C++ 边界(宏与预处理让语法树不稳),
不是实现缺陷:不做宏展开是 proposal 的非目标之一。产品侧的兜底是**能力明示**——
UI 标注跳转基于名称与语法树的启发式匹配、不承诺编译级精确,用户不会误以为这是编译级结果。

## 5b. 断言自查复核(任务 11.8 / design.md D8)

按产品阶段 2026-08-17 定的固定口径,对全部 165 条 E2E 断言与实测指标过两问:
> ① 功能没实现的话,它会不会照样成立?(假绿)
> ② 数字漂亮的话,它测的是不是我要保证的那条路径?(假数字)

**复核中查出并已修掉的 4 条:**

| 原断言 | 问题 | 处置 |
|---|---|---|
| `图片文件被跳过` / `二进制文件被跳过` | 违反②:只断言"结果里没有它们"。若待搜字符串**根本不在**那些文件里,断言照样绿 —— 测不到跳过逻辑 | 加**正向对照**:先在页内读出 `photo.svg` / `logo.svg` / `blob.bin` 的正文,断言它们**确实含**待搜字符串;二进制那条再加"本次搜索确实产出了命中"(`rows > 0`),排除"整个搜索没跑"的情况 |
| `索引不可用时主题切换仍可用` | 违反①:只检查按钮元素存在。主题功能整个坏掉也会绿 | 改成真的点一次并 `waitForFunction` 等 `body` 背景色变化,断言前后色值不同 |
| `切换项目后引用面板与全文搜索面板已关闭` | 违反①:切换前面板本来就是关的,这条恒绿 | 切换前**先跑一次全文搜索把面板打开**并断言其确实打开,把它作为前提纳入后一条断言 |
| `索引期间目录树可交互` | 违反①:只数 `.tree-row` 行数。索引即使阻塞了主线程,行数也可能已经 > 0 | 改成"确认顶栏确实显示**索引构建中**" + "真的展开 `pkg-00` 并等到 `f-NNN.go` 子项出现"三者同时成立 |

**复核确认无问题的模式:**
- 31 处 `check(名称, true)` 均紧跟在一个 `waitForFunction` / `waitForSelector` 之后 —— 等待失败会抛错并使整份报告失败,不构成假绿(等待本身就是断言)。
- P95 与"首批 < 1 s"两组数字已按②核过路径:P95 的 20 个目标符号名**全项目唯一**(带"目录_文件"双标签),
  确保走的是"打开目标文件"这条真实路径而非弹候选列表;计时在页内用 `performance.now()`,不含 CDP 往返。
- 跳过类断言(注释/字符串中的同名文本不计入引用)有天然正向对照:同一次断言里要求 `handler.go` / `client.go` **出现**、`service.go` **不出现**。

## 5c. 正交矩阵兜底走查(任务 11.9)

每格只能是三种之一:**具体断言名** / **明确的 n/a 理由** / **公开的空格(含不补的理由)**。
"已覆盖"三个字不算 —— 功能坏掉的话那种表照样是满的,正是第①问要防的东西。

### 矩阵 A:模式 × 候选情形(本次两处偏差就是这里的相邻两格)

| | 项目模式 | 单文件模式 |
|---|---|---|
| **唯一定义** | 「跨文件跳转到唯一定义且落点行号正确」 | 「单文件模式下文件内跳转可用」 |
| **多定义(重载)** | 「项目模式:同名重载弹候选列表且未自动跳转」;另有「同名多候选弹出候选列表」(`New`,跨文件) | 「单文件模式:同名重载同样弹候选列表且未自动跳转(不再静默跳第一条)」 |
| **定义 + 声明** | 「定义与其声明并存时直接定位到定义,不弹候选列表」;「项目模式:声明 + 唯一定义时落点在定义行」 | 「单文件模式:定义优先同样生效,落点在定义行而非声明行」 |
| **无定义** | 「未找到定义时给出提示」+「未找到定义时预览保持不变」 | 「单文件模式下目标不在本文件时出现引导提示」 |
| **符号未就绪** | 「索引未完成时跳转给出"仍在构建中"提示,不报错不空白」(索引暂停开关) | **⚠️ 本次由矩阵捞出** →「单文件模式:符号尚未抽取完成时提示"解析中"而非误导性的"打开所在文件夹"」 |
| **跨模式一致性** | 「同一文件同一标识符:单文件模式与项目模式跳转行为一致」(同一组探针跑两遍) | ← 同左 |

### 矩阵 B:语言支持档 × 能力

| | 大纲 | 跳转入口 | 查找引用入口 | 全局符号搜索 | 能力标识 |
|---|---|---|---|---|---|
| **full**(Py/Java/C/C++/Go/JS/TS) | 五语言各一条「大纲条目内容与行号正确」 | 「可在预览区 ⌘+点击标识符触发跳转」+「预览区右键菜单提供…」 | 「查找引用命中定义处与调用处」 | 「符号搜索选中结果:打开文件并定位到符号行」 | 「支持的语言显示"可跳转"能力标识」 |
| **outline-only**(Markdown) | 「.md 展示标题层级大纲」+「跳过围栏代码块内的 #」 | *空格* — 与 `.yaml` 共用同一段 `intelLevelByName(…) === 'full'` 判定,该分支已由下一行断言;本次不再单独补一条同机制断言 | *空格* — 同左(右键菜单与跳转受同一个 `intelOn` 门控) | **⚠️ 本次由矩阵捞出** →「Markdown 标题不进入全局符号搜索」 | 「.md 显示"仅大纲"能力标识」 |

### 矩阵 C:文件规模 / 索引状态 × 代码理解

| | 大纲 | 预览提示 | 跳转 |
|---|---|---|---|
| **正常文件** | 见矩阵 B | n/a — 无降级可提示 | 见矩阵 A |
| **> 5 MB(截断)** | 「超 5MB 文件的大纲区明示符号未被索引」 | 「超 5MB 文件的预览区明示截断与索引受限」 | *空格* — 未断言"在截断文件里触发跳转"。不补的理由:该文件根本没进索引,跳转会走**与"无定义"完全相同的那条分支**(矩阵 A 已覆盖),补这格是重复覆盖同一段代码 |
| **索引达上限(partial)** | n/a — 降级是项目级状态,不改变单文件大纲行为 | 「符号总数达上限时状态置 partial 并提示"项目过大"」+「降级提示包含已索引文件数」 | *空格* — 未断言"对未被收录的符号触发跳转"。理由同上,走"无定义"分支 |
| **Worker 异常(unavailable)** | *空格* — 未断言该状态下的大纲行为。理由:大纲走 `extractOne` 的独立通道,不依赖项目索引池,故不受该状态影响;本次未为此单独补断言 | 「抽取任务失败时提示"符号索引不可用"」 | 已实现「符号索引不可用,无法跳转」提示,但*未单独断言*(与"无定义"共用同一段 `showNotice` 分支) |

### 这次试用的结论(不是"好不好用",是具体捞到了什么)

**捞到 3 个格子**,都是前两道结构性防御没盖住的:

1. **单文件模式 × 符号未就绪** —— 项目模式有「索引仍在构建中」,单文件模式没有对应态。
   后果不是少个提示,而是**给出错误建议**:符号明明就在本文件里,却提示"打开所在文件夹可获得跨文件跳转"。
   已修(新增 `activeFileParsing` 信号 + 专用暂停钩子做确定性断言)。
2. **Markdown × 全局符号搜索** —— spec 写了 Markdown MUST NOT 提供跳转与查找引用,实现上靠
   "标题不进 `byLowerName`" 保证,但**没有任何断言证明它**。已补。
3. **不支持语言 × 跳转入口** —— 同上,靠 `intelOn` 门控保证,只断言了能力标识文案,
   没断言"入口确实不存在"。已补。

**三个格子的共同形状**:都不在"功能能不能用"这条线上,而在"**不该有的东西确实没有**"这条线上。
断言天然偏向证明存在,矩阵是逼着把"不存在"也逐格过一遍。

**成本与副作用(如实记录)**:
- 逐格填表本身不累,累的是**为填格子去核实现细节**——判断某格是 n/a 还是空格,得回去读一遍门控代码。
- 补第 3 格时踩了一个坑值得留档:对不支持的语言我们**故意不调 `preventDefault`**(让用户仍能用 Chrome 自带右键菜单),
  于是 E2E 里的真实右键会拉起**浏览器原生菜单并卡死整个标签页**。必须改用合成 `contextmenu` 事件。
  产品行为是对的,错的是测试手法 —— 这类"只在写测试时才暴露"的交互边界,矩阵不逼一遍就碰不到。
- **本次矩阵有 5 个公开空格**,都写明了不补的理由(重复覆盖同一分支 / 共用同一门控)。
  一张填满的矩阵反而可疑;这 5 个空格是这张表诚实的证据。

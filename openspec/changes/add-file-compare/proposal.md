> **本 change 只做 C1:「文件对比」。**
> 它**不是** git 对比,**对外也不许这么叫** —— 命名要诚实(PM 裁定)。
> 读 `.git` 做「工作区 vs HEAD」是 C2,**另立 change**,可行性结论见文末附录。

## Why

用户要「git 文件版本对比」。可行性探索的结论是走**路线 C:一个 diff 内核,分层解锁数据源**——
先把**渲染与算法**做出来(它跟"另一份内容从哪来"完全无关),再把数据源从"用户在项目里选的另一个文件"(C1)扩展到"HEAD 里的 blob"(C2)。

**C1 现在就能开工,不依赖任何未决问题**,并且它本身对用户有用:对比两份配置、对比两个相似实现、对比一份文件的两个副本。

**为什么先做 C1 而不是直接冲 C2**:C2 的唯一增量是一个只读 git 对象读取器,而它有一个**尚未关闭的可达性前置**(`.git` 的两个子问题,见附录),PM 已安排真机核验。**把 diff 内核压在那个前置后面,等于让一件能做的事去等一件不确定的事。**

## What Changes

在文件预览区新增一个**并排对比视图**:用户预览某个文件时,可选择**当前项目内**另一个文件与之并排对比,行级差异高亮。

- 对比目标**只从当前项目内选取**,**不新开系统文件选择器**(理由见 design 的 D1,三条,其中一条直接关系授权面)。
- 对比是预览区的一个**临时视图态**:不进导航栈,不改大纲归属,退出即回。
- 只读:两侧都拒绝修改,且**界面上不存在任何"接受/回退/合并"控件**。

## Non-Goals

- **不做 git**。读 `.git`、HEAD、commit、blob 全归 C2。
- 不做统一(unified/inline)视图 —— C1 的语义是"两份并列的文件",没有"哪份是基线"的先验;unified 视图内在地假设了基线。**用错语义比少一个视图贵。** C2 再评估。
- 不做三方合并、不做冲突解决、不做任何写操作(**只读是红线**)。
- 不做跨项目对比、不做目录级对比。
- 不把对比做成独立应用模式:目录树 / 大纲 / 跳转 / 搜索照常工作。

## Impact

- 新增:diff 内核 + 并排对比视图(`src/preview/`),对比目标选择动线(复用既有项目内文件检索)。
- 触及:预览区视图态、键盘帮助面板(新增快捷键)、E2E。
- **不变量:三条都不受影响**,`check-invariants.mjs` **不需要改**。**若新依赖引入了任何禁用符号,应当让它红,而不是放宽名单。**
- 文档:README 增加「文件对比」一节,**措辞 MUST NOT 让人以为这是 git diff**。

## 附录:C2(读 `.git`)的可行性结论 —— 存档,供 C2 立 change 时直接引用

**别重新推导,这些都是本机实测的。**

| 问题 | 结论 | 怎么测的 |
|---|---|---|
| 零网络下能不能解 zlib?要不要打包 pako? | **能,且不需要任何新依赖** | 浏览器原生 `DecompressionStream('deflate')` 直接解开本仓库的 loose object,还原出 `commit 194` 头 |
| 只读 loose object 够不够? | **不够,delta 是必答题** | 本仓库单个 pack:529 个对象里 **161 个是 delta(30%)**;克隆下来的仓库几乎全部对象都在 pack 里 |
| 需要自己实现 SHA-1 吗? | **不需要** | 读取路径只按十六进制对象名去 `.idx` 里查,从不对内容做哈希 |
| 13 MB 的 pack 要整个读进内存吗? | **不用** | FSA 给的是 `File`,可 `slice()` 按 idx 给的 offset 随机读 |
| 三条不变量会不会被破? | **一条都不破** | 读 `.git` 全是本地文件读;禁用符号表一条都不触发 |

**约束裁定:零网络 ✅ 只读 ✅ 空权限 ✅ —— 读 `.git` 不违反其中任何一条。**
真正的障碍是**可达性与复杂度**,不是不变量。这点不说清,容易把「难」误判成「违规」而错杀方案。

**C2 的可达性前置(G1),两个子问题:**

- **(a) Chrome 的 FSA 敏感目录黑名单会不会挡 `.git`?** 公开资料**两边都没有确证**。**MUST NOT 靠查资料结案。**
  便宜的实证:README 已写明 `.git` 是「collapsed rather than swallowed」,**产品自己的目录树就支持展开它**。**真机上展开一次能列出 `objects/`、`refs/`,(a) 就地关闭 —— 30 秒,不用写任何代码。** PM 已安排找用户做。
  (顺带:因此**我们对外并没有「不读 `.git`」的承诺**,C2 不与已发布文档冲突。)
- **(b) `.git` 有可能根本不是目录,而是一个文件 —— 已实证,无法绕开。**
  linked worktree / submodule 里的 `.git` 是文本文件,内容形如 `gitdir: /Users/…/.git/worktrees/<name>`,是**授权根目录之外的绝对路径**,FSA **从原理上到不了**(不能跨出用户选的根)。**写这份 proposal 的工作目录本身就是这种 worktree,`.git` 是 74 字节的文件。**
  → **C2 MUST 把「这是 worktree / submodule,读不到对象库」当成一等公民的降级路径**,说清原因,而不是报错或装作没这个功能。
- **(c) 这一格上,OPFS 夹具是结构性盲区。** E2E 用 OPFS 造合成项目,而 OPFS **按定义没有黑名单、也没有真实 worktree 布局**。**它在这一格绿了不算数,G1 MUST 真机人在环核验。**

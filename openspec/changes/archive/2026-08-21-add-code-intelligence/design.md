## Context

见 `proposal.md` 的 Why 与 `docs/prd-v0.2-reading-first.md`。本节只列影响方案选择的现状与约束。

**现状(已上线的 v0.1)**:主产物 `dist/assets/viewer-*.js` 937 KB(含 CodeMirror 6 与 15 种语言的 Lezer 语法);`src/search/indexWorker.ts` 已有一个只做目录遍历、分批回传相对路径的文件名索引 Worker,主线程 `searchStore.ts` 用**代次 token** 丢弃过期回包;`src/tree/treeStore.ts` 惰性加载 + 分批入列;`src/lib/fs.ts` 统一读取入口,5 MB 以上截断读前 1 MB,并有二进制嗅探与 UTF-8 边界处理;`src/preview/CodeView.tsx` 每次以只读 CM6 实例渲染;`public/manifest.json` 的 `permissions` 为空数组、无 `host_permissions`、无自定义 CSP。

**约束**:零网络、只读、不引入 LSP/tsserver、不接 AI/LLM;Chrome 122+ / MV3;跳转 P95 < 200 ms;新增依赖对体积的影响需论证(超过现产物 50% 需取舍论证);既有能力不得回归,`scripts/e2e.mjs` 现有 45 条断言必须仍全绿。

## Goals / Non-Goals

**Goals:**
- 符号抽取全部在 Worker 中完成,主线程只做派发与查询,索引期间既有交互零退化。
- 精度边界在 UI 与 spec 验收标准里都是显式的:哪些语言支持、依据什么匹配、多候选怎么办、超限怎么提示。
- 复用既有机制(代次 token、`fs.ts` 读取与降级、`filetypes.ts` 类型识别、localStorage 面板状态持久化),不引入平行体系。
- 为 change #2 预留:按文件的内容指纹 + 列式可序列化索引结构 + 统一的"文件 + 行"寻址通道(书签/已读态直接复用)。

**Non-Goals(设计层边界,超出 proposal 的非目标之外):**
- 不建标识符**反向索引**(所有出现位置)——查找引用改为按需扫描,理由见 D3。
- 不做正则搜索与替换(全文搜索只做字面量匹配 + 大小写开关)。
- 不缓存文件正文到内存或磁盘(全文搜索每次重新读盘)。
- 不做目录级增量索引(只做单文件级增量),理由见 D6。
- 不把任何键盘快捷键当作能力的唯一入口(理由见 D7),因此也不承诺某个键位在所有平台都能抢到。

## Decisions

### D0 贯穿性原则:分叉允许发生在机制层,不允许上浮到契约层

这个 change 里出现过两次同源的缺陷,修法也同源,提炼在此(PM 2026-08-18 措辞):

- **单文件模式跳转**:模式可以决定**候选集合怎么来**(机制),不能决定 **≥2 条要不要给候选列表**(契约)。
- **Markdown 富文本行定位**:渲染通道可以决定**怎么定位**(机制:滚到行 vs 滚到元素),不能决定**要不要定位**(契约)。

两次的病灶是同一个动作:**该留在机制层的分叉,漏上去污染了规则**。修法也是同一个:把规则往上提成不变量,让分叉点被压回机制层 —— 一次落在代码层(决策只有一份实现),一次落在契约层(requirement 只有一条不变量)。

**可当场自检的问题**(写下一个 `if`、或写一条按情形切分的 requirement 时问自己):

> **我这里分叉的是"怎么做",还是"要不要做"?**

分的是后者,基本就错了。

### D1 符号抽取:复用已打包的 Lezer 语法树(采用),不引入 tree-sitter WASM

四维对比(体积数据为本地实测,2026-08-17):

| 维度 | 复用 Lezer(采用) | tree-sitter WASM |
|---|---|---|
| **体积** | 新增 npm 运行时依赖 **0 个**(`@lezer/{python,java,cpp,go,javascript}` 已是 `@codemirror/lang-*` 的传递依赖)。**实现后实测(2026-08-17,阶段二快照 —— 收口时按任务 11.2 以最终产物重量,不要引用本行数字)**:主 chunk 936,990 → 962,965 B(**仅 +2.8%**),五套语法全部落在独立的 `symbolWorker` chunk(349 KB),不进首屏关键路径;js/css 总量 950 KB → 1,333 KB,**约 +40%**,高于估算的 +26% 但低于 50% 硬阈值。估算偏低的原因:Worker chunk 还要带 `@lezer/common`,且 Lezer 解析表本质是长字符串字面量、minify 几乎压不动 | `web-tree-sitter` 运行时 + 每语言一个 `.wasm`;官方发行的语言 wasm 普遍在数百 KB 到 MB 量级(C++ 最大),五种语言叠加为 MB 级,**大概率超过 +50% 阈值**(此项为数量级判断,未在本地实测) |
| **覆盖语言** | 现成覆盖 P0 需要的全部 5 套语法(JavaScript 语法通过方言参数同时覆盖 TS/JSX/TSX);另有 markdown/yaml/xml/html/css/json 可用于大纲扩展 | 覆盖面更广,但本次不需要更广 |
| **精度** | 均为**无类型信息的语法树**,两者在"能否识别定义位置"上没有本质差距。已实测确认 5 套语法都把定义位点标成可判别的节点(下表)。tree-sitter 的优势是社区现成的 `tags.scm` 查询,Lezer 需自己写节点映射 | 同为语法级;查询表现成可省一部分映射工作 |
| **实现成本** | 为 5 套语法各写一张"定义节点 → 符号种类"映射 + 祖先过滤规则(节点名已实测探明) | 新增依赖 + wasm 资源打包 + Worker 内 wasm 异步初始化生命周期 + **manifest 必须声明 `wasm-unsafe-eval`** |

**决定性理由是最后一条**:引入 WASM 必须为 MV3 放宽 CSP(`wasm-unsafe-eval`),这直接削弱 PRD P2 "零网络自证 / 最小声明面" 这个卖点 —— 而它恰恰是相对云端竞品的结构性优势。Lezer 路线让 `permissions: []` 与默认 CSP 保持原样。结论与 PM 的倾向一致,但理由不是"省事",是**安全声明面**加上**零新增依赖**加上**实测吞吐已够用**(见 D5)。

**实测的定义节点映射**(2026-08-17,用 node 直接跑项目内 `@lezer/*` 解析样例并 dump 节点名):

| 语言 | 定义节点 | 必须排除 |
|---|---|---|
| Python | `ClassDefinition` / `FunctionDefinition` 的直接子 `VariableName`;顶层 `AssignStatement` 的 `VariableName`(常量) | 嵌套函数体内的赋值 |
| Java | `Definition`,按**直接父节点白名单**收:父节点为 `ClassDeclaration` / `InterfaceDeclaration` / `EnumDeclaration` / `MethodDeclaration` / `EnumConstant`,或父节点为 `VariableDeclarator` **且该 `VariableDeclarator` 的父节点是 `FieldDeclaration`** | `FormalParameter` 下的 `Definition`(形参);`VariableDeclarator < LocalVariableDeclaration` 下的 `Definition`(局部变量) |
| Go | `FunctionDecl` / `TypeSpec` / `ConstSpec` / `VarSpec` 下的 `DefName`;`MethodDecl` 下的 `FieldName`(方法名)。方法的**容器是接收者类型**,位于 `MethodDecl → Parameters` 内、**不在方法名的祖先链上**,须单独取,否则容器恒为空 | `Parameter` 下的 `DefName`(形参);`PackageClause` 下的 `DefName`(`package main` 的包名) |
| C/C++ | `StructSpecifier` / `ClassSpecifier` 下 `TypeIdentifier`,**且该节点必须带 `FieldDeclarationList`**(枚举同理必须带 `EnumeratorList`)才算定义;`FunctionDefinition → FunctionDeclarator` 下 `Identifier` 或 `ScopedIdentifier` 末段;`TypeDefinition` 的**直接子** `TypeIdentifier`(即别名,`typedef struct Foo Bar` 取 `Bar`,不取嵌在 `StructSpecifier` 内的原类型名 `Foo`);`FieldDeclaration` 下 `FieldIdentifier`(类成员函数原型经此路径已收);`Declaration → FunctionDeclarator` 下 `Identifier`(**自由函数原型**,种类标为"声明");`PreprocDirective`(`#define`)下的**第一个** `Identifier`(宏名) | `ParameterDeclaration` 下 `Identifier`;`#define SQUARE(x)` 的**宏形参** —— 它与宏名同为 `Identifier < PreprocDirective`,只能靠位置区分;**作为形参类型出现的结构体**(如 `int utime(const char *, const struct utimbuf *);` 里的 `struct utimbuf`)与前向声明 —— 它们同样是 `StructSpecifier + TypeIdentifier`,但没有成员体 |
| JS/TS | `FunctionDeclaration` / `ClassDeclaration` 下 `VariableDefinition`;`MethodDeclaration` 下 `PropertyDefinition`;`InterfaceDeclaration` / `TypeAliasDeclaration` / `EnumDeclaration` 下 `TypeDefinition`;顶层 `VariableDeclaration` 下 `VariableDefinition` | `ParamList` 下的 `VariableDefinition`(形参)、函数体内的局部声明 |

**修正记录之二(2026-08-18,真实代码抽样时才暴露)**:上面"必须带成员体"这条不是洁癖 —— 不加这个条件,**每一处把结构体当形参类型用的地方都会多出一条假定义**(`const struct utimbuf *` 里的 `utimbuf` 会被当成定义)。在 400 个真实头文件样本上这一条消除了 **261 条误收(占样本总符号 3.7%)**。**合成样本测不出来,因为合成代码里没有"拿结构体当形参类型"这种写法** —— 这正是 D8 那两问要防的:样本只覆盖你想得到的写法,指标就只证明你想得到的部分。

**修正记录(2026-08-17,实现期实测 + 方案会话复核)**:本表初稿把 Java 规则写成"祖先集合命中",**那个写法按字面实现会收进每一个局部变量** —— 已复现验证:局部变量的祖先链是 `Definition < VariableDeclarator < LocalVariableDeclaration < Block < MethodDeclaration < ClassBody < ClassDeclaration`,`MethodDeclaration` 与 `ClassDeclaration` 都在允许集合里,字段与局部变量的**唯一**区别是 `VariableDeclarator` 的父节点是 `FieldDeclaration` 还是 `LocalVariableDeclaration`。因此规则收紧为**直接父节点白名单 + 名字位校验**,表中已改。表内 Go 包名、Go 方法容器位置、C 宏形参、typedef 别名、C/C++ 自由函数原型五处也是同一轮实测补上的。

**"按祖先过滤"是精度的关键**:Java 的形参与 Go 的形参用的是与真正定义**同一个节点名**,不过滤会把每个形参、每个局部变量都收成符号 —— 索引膨胀数倍,同名候选列表噪声爆炸,跳转直接失效。这条规则要进单元验证与 E2E 断言(形参不得出现在大纲与符号搜索里)。

### D2 索引架构:一次遍历 + Worker 池 + 全局代次

- **遍历只做一次**:扩展现有 `indexWorker.ts`,在 walk 时除相对路径外一并回传 `FileSystemFileHandle`(FSA 句柄可结构化克隆,项目里已靠这一点把根句柄传进 Worker 并存进 IndexedDB)。文件名索引继续只用路径,主线程把句柄按语言过滤后派进符号 Worker 池。避免"为符号索引再走一遍全树"。
- **符号 Worker 池**:`N = min(4, max(1, navigator.hardwareConcurrency - 1))`。每个 Worker 收 `{path, handle, langId}` 任务:`getFile()` → 超过 5 MB 直接回报"跳过(过大)" → `arrayBuffer` → UTF-8 解码(复用 `fs.ts` 的边界处理思路)→ Lezer 解析 → 按 D1 映射遍历抽符号 → 每约 200 个文件或 2,000 个符号回传一批。
- **全局代次**:把 `searchStore.ts` 的局部 token 提为一个模块级 `generation`,项目切换、目录树刷新时 `++`;文件名索引、符号索引、全文搜索共用它,过期回包统一丢弃。这样 spec 要求的"刷新后结果一致""切项目不残留"由同一个机制保证,不会出现三套各自漂移的失效逻辑。
- **主线程索引结构(列式)**:
  - `files: string[]`、`fileMeta: {size, lastModified}[]`
  - `symName: string[]`、`symKind: Uint8Array`、`symFile: Uint32Array`、`symLine: Uint32Array`、`symContainer: (string|null)[]`
  - `byLowerName: Map<string, number[]>` —— 跳转与符号搜索的唯一查询入口
- **降级原因必须随索引持久化**:文件若以"超大跳过"进索引,再次预览走缓存分支时**不能丢掉 `skipped` 标记** —— 否则大纲会把"文件过大,符号未被索引"错显成"未发现可列出的定义",直接违反 spec「截断文件须明示代码理解覆盖受限」。索引里按文件持久化降级原因(`fileSkip` 列),不靠调用方在内存里传递。
- **同名同行去重**:同一位置可能被两条规则各收一次(实测例:`typedef struct Node Node;` 在同一位置产出前向声明的 `Node` 与 typedef 别名的 `Node`),候选列表里就是两条一模一样的条目。索引写入时按"同名 + 同文件 + 同行"去重。
- **P95 < 200 ms 怎么达成**:跳转 = `byLowerName` 查表(内存 Map,微秒级)+ 打开目标文件。真正的耗时全在"打开文件"这条既有路径上(`getFile` + 解码 + 新建 CM6 实例),普通源码文件在现网实测远低于 200 ms;**同文件内定位不重读**(spec 已要求),只滚动 + 高亮,一帧内完成。**阶段二实测(2026-08-17)**:20 次跨文件跳转,中位 **17 ms**、P95 **17~18 ms**、最大 33~50 ms,远低于 200 ms 要求。计时用页内 `performance.now()`,从派发 `⌘`+点击到 `.cm-target-line` 出现在 DOM 为止、**不含 CDP 往返**,否则测的是 puppeteer 开销而非产品时延。测量样本必须保证符号名**全项目唯一**,否则跳转会退化成弹候选列表、根本不走打开文件那条路径,测出来的"快"是假的(实现期踩过这个坑)。

### D3 查找引用:按需扫描,不建反向索引

反向索引要存所有标识符出现位置,数量级是定义的 20~50 倍(10k 文件项目里是数百万条),内存与构建时间都不可接受,而查找引用是**低频操作**——用构建期换查询期不划算。

按需扫描的三级漏斗:
1. **候选文件筛选**:只扫该符号所属语言组的文件(由文件名索引提供清单)。
2. **廉价预筛**:读文件文本后先 `indexOf(name)`;整份文本没有该子串就直接跳过,不解析。绝大多数文件在这一级被淘汰。
3. **精筛**:只对命中文件做 Lezer 解析,按命中位置查所在节点类型,落在 `Comment` / `String` 类节点内的出现丢弃 —— 这正是 spec「排除注释与字符串」的实现依据,靠语法树而不是正则猜。

流式回传(每批 ≤50 条),命中数达 1,000 条即停并标注截断;另设扫描文件数/时间预算上限,超出也走截断提示。

**Markdown 富文本视图的行定位(2026-08-18 补)**:大纲条目携带的是**源码行号**,而富文本视图没有"行"。实现口径:在 markdown-it 渲染阶段利用 block token 的 `token.map[0]` 给标题元素打上 `data-cv-line` 属性,大纲点击时按该属性找到元素(取 ≤ 目标行的最近一个)滚动并短暂标识。净化侧沿用既有做法——`PURIFY_CONFIG.ADD_ATTR` 已有 `data-cv-path` 的先例,追加 `data-cv-line` 即可,不改净化策略。**两个渲染通道的机制不同是必然的(一个有行、一个没有),但契约只有一份**:"目标行 → 定位到可见区域 + 短暂标识",写在 file-preview 的不变量里。

### D4 全文搜索:同一个 Worker 池的另一类任务

复用符号池,任务类型 `grep`:`getFile` → 若 > 5 MB 只取前 1 MB(与预览截断阈值同源,用户心智一致)→ 复用 `filetypes.ts` 的 `identifyByName` + `looksBinary(前 8 KB)` 跳过图片与二进制 → 逐行字面量匹配(大小写开关只影响是否先 `toLowerCase`)。

取消(**2026-08-17 更正 —— 初稿写错了**):初稿写的是"`generation++` + 清空池任务队列",**照字面实现会把符号索引一起打掉**:全局代次是**索引**的失效标记,符号池在构造时捕获了它,搜索一次就 `++` 会让索引的在途回包全部作废、索引直接断掉。更正为:

- **每次扫描持有自己的 `runId`**,取消 = 丢弃旧扫描池 + 用 `runId` 判定回包是否过期;新查询、切大小写、关面板只动 `runId`,不碰全局代次。
- **扫描池同时仍捕获全局代次**,因此切项目 / 刷新目录树时它连同符号索引一并作废 —— 这两类事件本来就该同时废掉索引与在途搜索。
- Worker 在**文件循环边界**检查后自行退出(文件读取是 `await`,边界检查足以及时响应,不需要 `terminate` 重建)。

spec 要求的可见行为(过期结果不混排、切项目即停)完全不变,变的只是实现手段。教训与 D1 的 Java 规则同类:**"代次"对"索引失效"和"搜索取消"两件事的语义并不相同,不能共用一个计数器。**

不缓存正文:22 MB 级的正文常驻内存会与符号索引叠加,而全文搜索是低频操作,重新读盘可接受。

### D5 10,000 文件规模的耗时与内存预估(基于实测外推)

**实测吞吐**(2026-08-17,node 24 + 项目内 `@lezer/*`,本机;含 parse 与全树遍历):TS 4.1 KB / 1.05 ms、Go 2.6 KB / 0.72 ms、Java 3.0 KB / 0.61 ms、Python 2.8 KB / 0.67 ms、C++ 2.8 KB / 1.23 ms ⇒ **2~5 KB/ms**(C++ 最慢)。

**外推**(10,000 文件项目,假设 50~60% 属 P0 支持语言 ≈ 5,500 文件、平均 4 KB ≈ 22 MB 代码):
- 解析 + 抽取 CPU:22 MB ÷ 3.5 KB/ms ≈ **6.4 s 单线程**;4 Worker 并行 ≈ **1.6~2.5 s**
- 文件 I/O:FSA `getFile()` + `arrayBuffer()` 约 0.3~1 ms/文件 ⇒ 10,000 文件 **3~10 s**(可并行,是耗时主项)
- **合计预计 5~15 s**,全程在 Worker 内,主线程首屏与交互不受影响
- 内存:5,500 文件 × 约 30 个定义符号 ≈ **165,000 条**。列式存储下每条约 50~80 B(名字字符串 ~30 B + kind 1 B + fileIdx 4 B + line 4 B + container 引用 8 B)⇒ 10~14 MB;`byLowerName` 的 Map 与数字数组开销再 +10~20 MB ⇒ **总量 20~35 MB 量级**;按每条 ~200 B 的整体口径线性外推,400,000 符号上限下最坏约 **80 MB**(上限取值的讨论见下)。

**上限取值:400,000 条(修订)**。初稿取 200,000,但那个数字和我们的旗舰场景撞车:上面的外推本身就是 165,000 条(余量只有 21%),而那还是"只有 50~60% 文件属 P0 语言"的假设;换成 P0 占比 80% 以上的 Java / Go 单体仓,8,000 × 30 ≈ 240,000 直接触顶 —— 用户打开一个再普通不过的 10k Java 仓就看到"项目过大,符号索引仅部分完成",产品叙事被自己的阈值打脸。

上限应由**内存**约束,不该由一个恰好压在目标规模上的数字约束。400,000 条按同一口径估算约 80 MB(列式 24~32 MB + Map 与数组开销),对桌面 Chrome 单标签页可接受,同时仍保住"不无限膨胀"的下界。**判据写进 spec**:约 10,000 文件的典型项目(含 P0 语言占比 80% 以上的单体仓)MUST NOT 进入部分完成状态。

**为什么不做按内存自适应**:`performance.memory` 只有 Chrome 有、读数被量化且统计的是**整个标签页**的堆(含 CodeMirror 文档与 DOM),把它当索引预算会让降级时机随页面其它状态漂移;`measureUserAgentSpecificMemory()` 更准但是异步、需要跨源隔离,在扩展页里为此加隔离头不值当。固定阈值的好处是**可判定、可 E2E 断言**——降级行为的可验收性比多榨几 MB 更重要。自适应留给 change #2 在有真实内存数据后再议。

**降级的用户可见行为**由 spec「索引规模降级」规定(部分完成提示 + 已索引文件数、截断文件明示、Worker 失败提示),此处只定实现口径:计数达上限即停止收录并上报状态,不是抛错。

**校验义务**:任务清单要求开发会话在 10,000 文件 OPFS 合成项目上记录真实索引耗时与 JS heap 数值;与本预估偏差超过 2 倍时**回报 PM 调整上限**,不擅自改阈值。

**实测回填(2026-08-17,阶段一,详见 `docs/spike-code-intel-baseline.md` 第 3 节)**:10,000 文件 / 支持语言占比 85% / **306,000 符号** → 索引 **2.1–2.2 s**、JS heap **39–44 MB**、根层首屏 **7 ms**、终态"索引已完成"。**判据满足**(未进入 `partial`),且这组数据反过来验证了把上限从 200,000 提到 400,000 是必需的 —— 若仍是 200,000,这个再普通不过的场景会直接触顶降级。内存优于按 200 B/符号的线性外推(应为 61 MB),说明列式存储的实际开销低于估算。

**C/C++ 符号密度实测(2026-08-18,PM 观察项收口)**:C/C++ 样本密度为 Go 对照组的 **0.13×**,远未达"2 倍即复看阈值"的线,**400,000 上限无需调整**。但要说清比值为何这么低:对照组的 Go 是**刻意堆砌的高密度合成代码**(25.95 符号/KB),真实代码到不了这个密度。反过来说明**阶段一那次 306,000 符号的测量本身就偏保守**,真实的万级 C/C++ 仓只会更少 —— 阈值余量比 23% 更宽。

**耗时比预估快 2 倍以上,但这不是可外推的结论**:合成项目建在 **OPFS** 上,而上面 3~10 s 的 I/O 估算针对的是**真实磁盘目录的 FSA 句柄**;OPFS 的 `getFile()`/`arrayBuffer()` 明显更快,几乎把 I/O 这一项抹平了 —— 实测总耗时与"4 Worker 并行解析 1.6~2.5 s"的 CPU 估算吻合,恰好印证瓶颈在 I/O。**因此 2.1 s 是 CPU 受限的下界,不是用户真机打开真实 10k 仓库的预期值**,真机数值应介于两者之间。真实磁盘的测量需要用户手势选目录、无法自动化,已作为人工项列入任务 12.8,且**不设为门禁** —— spec 里对用户的承诺是"首屏 < 1 s、进度可见、索引期间不阻塞"这三条可断言的行为,而非某个绝对秒数。

### D6 持久化:P0 不落 IndexedDB(结论),但把钩子埋好

落盘的收益只有"省掉解析 CPU"(并行后约 2 s);成本是约 30 MB 序列化写入,**且复用前必须校验指纹,而校验 10,000 个文件的 size/lastModified 需要对每个文件 `getFile()`——那正是耗时主项(3~10 s)**。收益远小于成本。加上陈旧索引与既有 spec「MUST NOT 展示过期缓存」的精神冲突,P0 结论:**内存索引,项目会话内驻留,重开重建**。

已埋的钩子(change #2 若要落盘无需重构):索引按文件记录 `{size, lastModified}` 指纹(spec 已要求)、索引结构为列式可直接序列化;届时只需加一层 IDB store 与"整项目指纹摘要"的比对策略。

**失效策略**:
- **单文件级增量(做)**:预览某文件时对比指纹,不一致就地重抽该文件符号。成本 O(1),解决"外部改了一个文件后大纲/跳转行号过期"这个高频痛点。
- **目录树刷新(全量重建)**:`generation++` 后全量重建,与现有文件名索引一致。**不做目录级增量**——FSA 没有变更通知,要判断"哪些文件变了"本身就得全量 `getFile()` 扫描,增量省不掉主要成本,只增加一套可能出错的状态机。

### D7 UI 布局与快捷键

- **大纲**:预览区右侧窄栏,可折叠;折叠态与宽度沿用侧栏宽度那套 localStorage 持久化做法(同一套 key 命名风格),不引入新机制。
- **查找引用 / 全文搜索结果**:预览区下方抽屉面板,可关闭;两者共用列表组件(按文件分组 + 行号 + 行片段 + 命中高亮)。
- **多候选列表**:复用符号搜索下拉的组件与样式,只换数据源。
- **单文件模式(修订补齐)**:大纲照常提供(单文件抽取一次即可,成本 O(1));跳转限定当前文件内,目标不在本文件时给提示并引导"打开所在文件夹";引用与全局符号搜索入口不渲染,原地给出需要打开文件夹的说明。实现上单文件模式复用同一套抽取代码,只是索引里只有一个文件、`byLowerName` 的查询结果天然只可能落在本文件 —— 不需要第二条代码路径,只需要 UI 层按 `mode === 'single'` 决定渲染哪些入口与提示。
- **能力标识**:预览区 header 显示语言名 + "可跳转 / 仅高亮" 徽标 + 索引状态(构建中 N/进度、已完成、部分完成、不可用),对应 spec「支持范围与能力明示」与「索引规模降级」。
- **键盘只是便捷层(修订后的核心原则)**:初稿把 `F12` / `⌘⇧O` 当成一等入口,这是错的 —— 见下面的冲突表。修订后的口径是:**每项能力都必须有一个不依赖快捷键的界面入口**(按钮 / 右键菜单 / 搜索面板的模式切换),快捷键叠加在上面。这样任何一个键位被浏览器抢占,能力都不会跟着失效,验收也不必去证明"浏览器没抢走这个键"这种不可证的事。
- **触发方式**:跳转 = `Cmd/Ctrl` + 点击标识符(主)+ 预览区右键菜单项(主);查找引用 = 右键菜单项(主)+ `Shift+F12`(补充);导航栈 = 界面上的后退/前进按钮(主)+ `Alt+←→`(补充);符号搜索与全文搜索 = 搜索面板模式切换(主)+ 平台键位(补充)。
- **快捷键冲突核查(修订:初稿此处有两处错误)**:

### D8 E2E 验收方式

沿用 `scripts/e2e.mjs` 既有惯例:真实 Chrome(`headless:false`)+ CDP `installExtension` 装载 dev 构建 + OPFS 合成项目 + `window.__cv` 测试钩子(仅 dev 构建)+ `page.on('request')` 网络监控。

新增一个**代码理解合成项目**:Go / TS / Java / Python / C++ 各若干文件,刻意构造(a)跨文件唯一定义、(b)两处同名定义、(c)注释与字符串里出现同名文本、(d)带形参与局部变量同名的函数、(e)一个 `.yaml` 与一个 `.md`(不支持/仅大纲两种标识)、(f)一个 50 MB 大文件。

新增断言(要点):大纲条目内容正确且**不含形参**;跨文件跳转落点行号正确;同名多候选**出现列表且未自动跳转**;`Alt+←` 回到原文件原行且**页面 URL 未变**;查找引用条数正确且注释/字符串中的同名文本被排除;`⌘⇧O` 与 `⌘K` 对同一关键词的结果集不同;`⌘⇧F` 首批结果 < 1 s 且点击直达行;不支持语言显示明示标识;10,000 文件项目下首层仍 < 1 s 且索引进度可见;50 MB 文件出现"索引受限"提示;**全程 `httpRequests` 为空**;跳转 20 次的 P95 < 200 ms(`page.evaluate` 内用 `performance.now()` 记录触发到目标行可见的时延)。

**E2E 覆盖不到的部分(必须如实标注,不许假绿)**:CDP `Input.dispatchKeyEvent` 派发的是合成事件,只进入渲染进程,**根本不会触发浏览器 UI 的快捷键**。所以"按 `Alt+←` 后页面 URL 未变"这类断言在开发有没有写 `preventDefault` 的两种情况下都会绿 —— 它证明不了任何事,不能作为键位冲突的验收证据。修订后的分工:

- **E2E 断言可断言的部分**:导航栈语义(回到原文件原行、端点不报错、按钮置灰)、以及 `keydown` 处理器确实调用了 `preventDefault`(dev 钩子里记录 `defaultPrevented`)。断言旁必须注明"浏览器级后退/前进行为不可由 E2E 覆盖"。
- **人工真机验证清单**:`Alt+←/→`、符号搜索键位、`⌘⇧F`、`F12`(若保留)在 **macOS 与 Windows 两套 Chrome** 上的真实按键行为,逐项记录验证人、操作系统、Chrome 版本与日期。这沿用项目既有惯例 —— E2E 覆盖不到的场景要在 tasks 里如实写明,而不是用一条会自动变绿的断言糊过去(上一个 change 的 7.1 就是这么处理授权路径的)。

**本项目固定的断言自查口径(PM 2026-08-17 定,阶段三与收口逐条按它自查)**:这个 change 里已经出现三次同类事件 —— ① `Alt+←` 的"URL 未变"断言(功能没实现也会绿);② 大纲"不残留"只断言最终态(异步 effect 迟早会清空,恒绿);③ P95 测量样本的符号名重复,跳转全退化成弹候选列表(测的根本不是打开文件那条路径,"快"是假快)。**同一个病:验收动作看起来在验,其实验的东西跟要保证的东西不是一回事。** 三次说明这是这类项目的系统性风险,不是偶发。因此拿到任何一条断言或指标,先问两句:

> **1. 功能没实现的话,它会不会照样成立?**
> **2. 数字漂亮的话,它测的是不是我要保证的那条路径?**

答不上第一句就是假绿断言,答不上第二句就是假数字。两者都比没有断言更糟,因为它们制造"已验证"的假象。

**统一的病灶:断言的覆盖面比 requirement 窄(2026-08-18 由开发会话归纳)**。下面两块原本记成两条独立教训,其实是同一个病的两个方向 —— 一个是**横向窄**(只证明"存在",不证明"不存在"),一个是**纵向窄**(只覆盖 Scenario 的前半句,后半句没人验)。判据因此可以合成一句:**逐条把 requirement / Scenario 的每个分句拿出来,问"哪条断言证明了这一句"** —— 覆盖不到的分句就是洞,不管它是排除类条款还是后半句。

**断言天然偏向证明"存在",MUST 专门检查"排除类 requirement"(2026-08-18,11.9 正交矩阵试用的结论)**:矩阵走查捞出 3 个格子(单文件模式 × 符号未就绪、Markdown × 全局符号搜索、不支持语言 × 跳转入口),**三者的共同形状是它们都不在"功能能不能用"这条线上,而在"不该有的东西确实没有"这条线上** —— spec 里凡是写 MUST NOT / SHALL NOT 的条款(不提供某入口、不收录某类符号、不展示某提示),实现往往靠一处门控保证,而断言只覆盖了正向文案、没有证明"入口确实不存在"。

因此**比整张矩阵更省力的做法是:直接把 spec 里所有 MUST NOT / SHALL NOT 条款列出来,逐条问"有断言证明它吗"**。矩阵的价值在于它逼着把"不存在"也逐格过一遍;认出这个形状之后,可以直接按形状查而不必每次叉乘。

矩阵本身与 5 个**公开空格**(照实留空 + 不补的理由)见 `docs/spike-code-intel-baseline.md` 第 5c 节。

**矩阵的边界(2026-08-18,用户真机实测打出来的一课)**:用户装上跑,报出"Markdown 大纲点击不能定位" —— 一条**违反已批准 spec** 的缺陷,而全套自动化 + 矩阵走查都没抓到。两层原因叠在一起:

1. E2E 断言了「`.md` 显示标题大纲」,**只证明了大纲存在,没证明它能用** —— Scenario 的后半句"并可点击定位"被吃掉了。这与"排除类条款缺断言"是同一个病的另一面:**断言只覆盖了 Scenario 的前半句就绿了**。
2. **矩阵能捞到的只有你想到要叉乘的维度;漏掉的维度整行都不会出现在表上,连空格都不会留** —— 换句话说,**矩阵的盲区不是空格,是缺失的行**(开发会话措辞)。空格是可见的、会被追问的;缺失的行连被追问的机会都没有。因此**填矩阵之前先问一句:有没有哪条 requirement 存在两条实现路径,而我只列了一条?** 矩阵选的维度是「模式 × 候选情形」「语言档 × 能力」「规模 × 状态」,**没把「Markdown 富文本 / 源码双视图」当成一个维度** —— 而 `MarkdownView` 与 `CodeView` 显然是两条代码路径。选维度的判据仍是那条:**凡会改变代码路径的分支都是维度**。

**结论:验收体系再严也替代不了真人打开用一遍。** 三道防御(不变量式 requirement、无第二条决策路径、正交矩阵)都是"在已知的形状里查得更细",真人试用是唯一能撞见"没人想到过的形状"的手段。change #2 的验收 MUST 含真人试用环节。

**回归门禁**:既有 45 条断言必须仍全绿,新增断言与其合并在同一份报告中输出。

## Risks / Trade-offs

- **[启发式跳转让用户误以为是编译级精确]** → UI 明示"基于名称匹配"、多候选强制给列表不自动猜、精度边界写进 spec 的验收标准(不只是文档角落)。
- **[产物体积 +26%]** → Worker chunk 是独立异步 chunk,不进首屏关键路径;任务清单含构建后实测校验,超出预估需回报。
- **[C/C++ 精度最低:宏与预处理让语法树不稳,且解析最慢(2 KB/ms)]** → C/C++ 按 PRD 要求保留在 P0;若实测显示噪声高到影响可用,**降级为"仅大纲、不跳转"并回报 PM**,不擅自缩小 spec 范围。判定不靠主观感受,用三个可判定指标(任一超阈值即回报):① **误收率** = (被收成符号的形参 + 局部变量数) / 总符号数 ≤ 5%;② **多候选列表中位长度** ≤ 3;③ **定义漏收率**(对样本中人工标注的定义)≤ 15%。样本 = E2E 合成 C/C++ 文件 + 一个真实开源 C/C++ 项目的抽样文件。
- **[Java/Go 形参与定义共用节点名,过滤写错即索引污染]** → D1 的祖先过滤表 + E2E 明确断言形参不出现。
- **[10k 文件 I/O 拖长索引]** → Worker 池并行 + 进度可见 + 索引期间既有功能全部可用 + 超限有明示降级。
- **[`Alt+←` 触发浏览器后退,离开 viewer]** → `preventDefault` + E2E 断言 URL 未变。
- **[全文搜索每次重新读盘,大项目偏慢]** → `indexOf` 预筛 + 流式首批 < 1 s + 可取消 + 上限截断;以不缓存正文换内存可控,取舍已明示。
- **[内存/耗时外推偏乐观]** → 任务要求实测记录,偏差 > 2 倍回报 PM 调整上限。

## Migration Plan

纯增量:无数据迁移,IndexedDB schema 不变(不新增 store),manifest 不变。回滚 = 撤销新增模块的代码,既有能力不依赖新模块。

分三阶段交付,每阶段独立可验收:阶段一 = 索引 + 大纲 + 全局符号搜索;阶段二 = 跳转到定义 + 多候选列表 + 导航栈 + 查找引用;阶段三 = 全文内容搜索。任一阶段结束都能停下来发布而不留半成品入口(未完成的功能不出现在 UI 上)。

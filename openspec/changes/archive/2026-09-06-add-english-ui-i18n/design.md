## 决策

### D1:自研轻量表,不用第三方 i18n 库

选 key→翻译表 + 一个 `lang` 信号,理由:
- 规模小(~200 串、2 种语言),i18next 之类的复数/命名空间/异步加载能力用不上,徒增依赖与体积。
- 与项目既有取向一致:`theme.ts` 就是"signal + localStorage"的极简状态;i18n 照抄同一形状,读者不必再学一套。
- **可自证**:零网络、只读、无第三方运行时是项目的核心承诺,i18n 不该成为第一个"为了方便引了个库"的破口。

### D2:`t()` 靠 signal 读取实现响应式,而非 Context/Provider

`t(key)` 内部读 `lang.value`。Preact signals 在组件渲染期追踪 signal 读取,因此**任何在渲染中调用 `t()` 的组件都会自动订阅 `lang`** —— 切换语言即时重渲染,无需 `LangProvider`、无需 `useTranslation` hook、无需给每个组件传 prop。代价:在渲染之外(如事件回调里构造的一次性提示串)调用 `t()` 拿的是"调用时"的语言,不会随后续切换更新 —— 这对提示类文案可接受(下次触发即新语言)。

### D3:缺键三级回退,让迁移可增量

`messages[lang][key] ?? messages.zh[key] ?? key`。迁移期英文表只填了一部分,未填的键回退中文原文而不是空白/报错。于是"逐面板翻译"是安全的:翻一个面板,该面板变双语,其余仍中文可用,不会中途出现半渲染的空洞。key 本身作为最终兜底,漏建的 key 会以可见的 `welcome.foo` 形式暴露,便于发现。

### D4:默认语言是唯一裁定点,浏览器探测先关着

`initialLang()`:`localStorage` 存值优先 → 否则看 `DETECT_BROWSER_LANG`。该开关现为 `false`(默认中文),因为此刻只有样板面板有英文,若非中文浏览器默认英文会得到割裂体验。英文覆盖达标后置 `true`,`navigator.language` 非 `zh-*` 即默认英文,回退链保证过程平滑。把它做成**一处布尔开关 + 明确注释**,而不是散落的条件判断,是为了让 PM 的这条决定只需改一行。

### D5:CJK 字体栈与语言解耦

语言切换只改文案与 `<html lang>`,**不动 `styles.css` 的 `font-family`**。中英混排在同一字体栈下即可(系统字体栈对拉丁与 CJK 都有合理回退);不因语言切换重排字体,避免布局抖动与额外的字体加载策略。

### D6:样板选入口页(Welcome)

选 Welcome 而非顶栏其余按钮做样板,因为它:①自足(不牵连大量其他组件);②高可见(首屏);③同时含静态串与**带占位符的动态串**(相对时间),一个面板就能证明机制的两条路径。语言开关本身放顶栏(最终归宿),这样在 Welcome 屏也可见、可切,样板闭环。

## 迁移路线(供批量阶段参考,本次不执行)

1. 按面板分批:每批把一个组件的可见文案抽成 key、填双语、组件改走 `t()`。建议顺序 topbar 其余 → Tree → Preview/能力标识 → Outline/Reference/Search 面板 → KeyboardHelp(+ keys.ts 动作标签)→ 各类提示/进度/降级串。
2. 每批同步把该面板相关的 E2E 文案断言改为**语言无关**(锁 `lang='zh'` 或改用 class/`data-*`)。
3. 全部完成后,把 `DETECT_BROWSER_LANG` 置 true,并补一条"语言切换后既有交互不回归"的 E2E。

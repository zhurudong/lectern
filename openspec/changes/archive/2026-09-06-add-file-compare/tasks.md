## 1. 决策闸:diff 内核选型(先出数字,再选)

- [x] 1.1 实现一个**最小可跑的行级 diff + 并排渲染**,两种方案各做到"能对比两份文本并高亮行差异"为止 —— **只为拿数字,不做完整功能。**
- [x] 1.2 **测体积增量,按下面这个测法,MUST NOT 用别的:**
      量的是 **`dist/assets/viewer-*.js` 的 min+gzip 差值**(接入前 vs 接入后),**不是 npm 包自身体积**。
      后者会把我们**已经在打包**的 `@codemirror/state|view|language` 重复计进去,给出一个偏大且错误的数字 —— **那个数字会让我们基于假证据否掉正确的选项。**
      基线已实测:`viewer-*.js` 1.06 MB(min),`dist` 1.4 MB,上架 zip ≈ 518 KB。
- [x] 1.3 **已拍板(2026-08-28,PM):用 `@codemirror/merge` 6.12.2(MIT)。** 实测 +7,985 B ≈ 7.8 KB min+gzip,为门槛(~60 KB)的 1/8。
      决定性理由不是体积:手写版的 +558 B 是**只有算法、且上不了线**的价钱(不相似文件上 10,000 行吃 2.1 GB 内存 = 崩页)。**这不是 7.8 KB vs 558 B,是"能上线 vs 不能上线"。**
- [x] 1.4 **依赖已获用户批准(2026-08-28,经 PM 转达)。** PM 转达时连 7.8 KB / 门槛 1/8 / 回退代价更高一并说明,用户在信息完整的前提下放行。
      (留档:**若日后要退回自研,回退方案 MUST NOT 是那份 558 B 的实现** —— 那个报价已被证明是低估的。回退意味着自己实现线性空间分治的 Myers,**行数、正确性负担与随机化对拍测试全部要重新估、重新量,不得沿用任何既有数字。**)
- [x] 1.5 `@codemirror/merge@^6.12.2` 已写进 `package.json` 与 `package-lock.json`。
      **lock 只有新增、没有任何既有包被改版**(21 行全是 `+`)—— 即之前实测时见到的 `^` 传递依赖漂移**是 `--no-package-lock` 造成的,不是这次引入带来的**;lock 生效后 `@codemirror/view` 等已回到 6.43.8 等基线版本。
      `npm run build && npm run check` 绿。

## 6. 截断:差异会**假**(D4)

- [x] 6.1 阈值**沿用** `lib/fs.ts` 的 `SIZE_LIMIT` / `TRUNCATE_BYTES`,**MUST NOT 在对比侧另写一套** —— 两处各一套阈值就是接缝的物理形态。
- [x] 6.2 任一侧被截断时,**在对比视图内**明示"只覆盖已加载部分,未加载部分的差异未知"。
- [x] 6.2b **截断(6.2)与近似比对(8.2)在 spec 里是同一条要求的两个来源,实现时 MUST NOT 做成两套互不知情的提示机制。** 用户看到的是同一件事:**这次结论不可靠**。
- [x] 6.3 **断言 MUST 走「直接进对比态」这条动线**(即用例**不许**先在普通预览里打开过那个大文件)。
      用例一旦抄了"先普通预览、再进对比"的捷径,就永远测不到"用户直接进对比"这条真人走得通的路 —— **本项目已经在这个形状上吃过一次亏(全文面板的假绿:用例直接 `focus()` 到列表,跳过了触发缺陷的那一步)。**
- [x] 6.4 **夹具自检要写成断言**:确认那个大文件**确实触发了截断**(而不是夹具太小、根本没截断,于是断言在一个不存在的前提上绿了)。**"精心构造的前提"都要有断言证明它被构造出来了。**

## 8. 性能(D8)

- [x] 8.1 先主线程实现,**实测**不同规模下的 diff 耗时。
- [x] 8.2 **改用时间预算 + 精度自报,不要拍规模门槛**(依据见 design 实测):设 `DiffConfig.timeout`,并把 `Chunk.precise === false` **明示给用户**。
      理由:规模门槛要拍一个数,而"5000 行"和"5000 行只改了两行"的代价差十倍;时间预算是**自限的**,`precise` 是**自报的**。
- [x] 8.3 **MUST NOT 直接沿用 `MergeView` 默认的 `scanLimit: 500`。** 实测:它按**字符**计,16 KB 以上的文件会**悄悄退化成"整份都变了"**——一个看起来完整、实际错误的结论。**这是新要求②那类问题,不是性能问题。**
- [x] 8.4 加断言:一份 32 KB、只改了几行的文件,对比结果**不是**"整份都变了"。**这条断言必须红过一次**(用默认 `scanLimit` 跑一次,确认它变红)。
- [x] 8.5 只有当实测证明需要,才进 Worker。**MUST NOT 提前上 Worker** —— 序列化与状态同步的复杂度要有数字支撑。

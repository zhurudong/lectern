## Context

`src/tree/Tree.tsx` 现状:虚拟滚动(`ROW_HEIGHT = 24`,只渲染 `rows.slice(start, end)`,行用 `position: absolute` 定位),`visibleRows()` 已把"已展开层级下的可见行"扁平化成数组 —— **键盘导航要的行序模型已经现成**,不必新建。缺的是焦点与键盘事件。无 `role` / `tabIndex` / `onKeyDown`。

流程重量按改动重量:本文件只记两个决定实现成败的选择。

## Goals / Non-Goals

**Goals:** 纯键盘走完导航链路;活动行在虚拟滚动下不丢;焦点不与搜索框打架;两主题下焦点标识都可见。

**Non-Goals:** 自定义键位、多选、拖拽/重命名(只读定位不变)、树内输入型交互。

## Decisions

### D1 焦点留在容器上,用 `aria-activedescendant` 指向活动行 —— 不用 roving tabindex

WAI-ARIA `tree` 有两种焦点管理法,这里**只有一种能用**:

- **roving tabindex**(把 `tabindex=0` 轮转到活动行元素上,并对该元素 `.focus()`):**在虚拟滚动下必然出问题** —— 活动行滚出渲染范围就被卸载,**DOM 焦点随之丢失并回落到 `<body>`**,后续按键完全失效。这正是"焦点行被虚拟化卸载后焦点不能丢"这条要求的技术根源。
- **`aria-activedescendant`**(容器是唯一可聚焦元素 `tabindex=0` + `role=tree`,活动行只是被 `id` 引用的 `role=treeitem`):**DOM 焦点从不离开容器**,行被卸载只是少了一个被引用的元素,活动状态存在 JS 状态里(活动行的**路径**,不是索引也不是 DOM 引用),不受渲染范围影响。

**采用后者。** 附带解决第二个问题:键盘处理器挂在容器上,**只在目录树自身持有焦点时触发** —— 搜索框聚焦时事件根本不进树,不需要额外写"判断焦点在不在别处"的防御逻辑。**用焦点归属天然分流,好过用条件判断人为分流。**

**活动行用路径(`string[]`)标识,不用行索引**:展开/折叠/刷新都会重排行序,索引会指向另一行;路径在结构变化后仍指向同一个节点,找不到时(该节点已消失)再回退到最近的可定位行。

### D2 行序与层级操作全部复用 `visibleRows()`,不新建遍历

- `↑`/`↓` = 在 `visibleRows()` 结果里取相邻行;`Home`/`End` = 首/末行。
- `→` 展开 = 复用既有 `toggleDir`;`→` 进子项 = 展开后取下一行(扁平化后子项必然紧随父项)。
- `←` 回父级 = 活动路径 `slice(0, -1)`,再在 `visibleRows()` 中定位该路径 —— **不需要父指针**。
- `Enter` = 文件走既有 `onRowClick`(与鼠标点击**同一条通道**),目录走 `toggleDir`。

**MUST NOT 为键盘另写一套"打开文件"或"展开目录"的实现** —— 键盘与鼠标只是入口不同,行为契约同一份。这是本项目 D0 原则(分叉允许在机制层、不允许上浮到契约层)的又一次应用:**入口是机制,行为是契约。**

滚回视口:活动行索引 × `ROW_HEIGHT` 与当前 `scrollTop` / `viewport` 比较,越界则 `scrollTo`。

## Risks / Trade-offs

- **[`aria-activedescendant` 的辅助技术支持不如 roving tabindex 均匀]** → 但 roving 在虚拟滚动下**根本不工作**,不是取舍而是唯一可行解;辅以正确的 `role` / `aria-expanded` / `aria-level` 语义。
- **[活动行标识与选中标识混淆]** → spec 要求两者可区分;实现上用不同视觉手段(焦点环 vs 背景填充),两主题各定值,视觉自检必看这一项。
- **[长按方向键连续移动时每步都 `scrollTo` 造成抖动]** → 仅在越界时滚动,且滚动量取"刚好进入视口"而非居中。
- **[改 `Tree.tsx` 与后续视觉升级冲突]** → 本 change 先完成并发布,视觉升级紧随,不并行改同一文件。

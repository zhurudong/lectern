## Context

现状(已核实):
- **目录树**已有完整键盘导航(容器 `role=tree` + `tabIndex=0` + `aria-activedescendant`,活动行用路径标识);
- **预览区** `CodeView` 同时设了 `EditorState.readOnly.of(true)` **与** `EditorView.editable.of(false)`,且**没有任何 keymap**;
- **大纲** `OutlinePanel` 中 `onKeyDown` / `tabIndex` / `role` **零命中** —— 纯鼠标。

## Goals / Non-Goals

**Goals:** 一套**成体系**的键位;三面板皆可键盘到达与操作;焦点态可见;新键位全部避开浏览器保留键并进人工核验台账。

**Non-Goals:** 不做可自定义键位;不做 vim/emacs 模式;**不开放编辑**(只读定位不变);不改跳转/引用的行为与精度口径。

## Decisions

### D1 面板切换用 **Tab 序**兜底,专用键位只作便捷层

**F6 是浏览器保留键**(聚焦地址栏/工具栏),`Cmd/Ctrl+数字` 是切标签页 —— 两个"标准答案"都不能用。

**但这里根本不需要发明键位**:三个面板各给一个 `tabIndex=0` 的焦点容器,按 DOM 顺序(目录树 → 预览 → 大纲)排进**原生 Tab 序**,`Tab` / `Shift+Tab` 即可循环。

- **零冲突**:Tab 是平台原生焦点移动,没有任何浏览器会抢它;
- **零核验成本**:不需要真机验"它有没有被抢";
- **屏幕阅读器用户本来就是这么用的** —— 我们不是在发明交互,是在**补上一个本该有的可访问性基线**。

**代价要说清**:Tab 序里还有顶栏的搜索框与按钮,所以"下一个面板"可能需要按几次 Tab。因此**允许再叠一个专用键位作便捷层** —— 但它是 optional 的,**基线由 Tab 保证**。专用键位候选见 D4,一律**待真机核验后才写死**。

> 这是既有口径的又一次应用:**能用平台原生机制的,别自创键位**;自创的每一个键位都要付"它会不会被抢"的核验成本,而 Tab 不用付。

### D2 预览区光标:**病根是我们自己加的那道冗余保险**

`CodeView` 的注释写着"`readOnly` + `editable(false)` **双保险只读**"。而 **`editable(false)` 会关掉 contentEditable —— 光标与键盘导航正是随它一起没的。**

关键在于:**`readOnly: true` 本身已经完全禁止编辑**,`editable(false)` 对"防止修改"是**冗余**的;它唯一的额外效果,恰恰是**砍掉我们现在想要的东西**。

**改法**:去掉 `editable(false)`,保留 `readOnly: true`,并加入**光标移动 keymap**(方向键 / PageUp/Down / Home/End / 选区扩展),不引入任何编辑命令。

**必须一并验证的两件事**(去掉一道保险就要证明它确实冗余):
1. **确无任何写入路径**:输入、粘贴、拖放、IME 组合、右键菜单的"粘贴"全部不得改变文档内容 —— 既有 spec 的「只读保证」Scenario 要扩到覆盖这些路径;
2. **contentEditable 打开后的附带面**:浏览器拼写检查、IME 组合框可能附着到代码区。需实测观感与性能,必要时以属性关闭拼写检查。

> **教训值得记在原地**:"双保险"听起来只有好处,**而这道保险的成本在两个月后才显形** —— 它挡住的不是错误,是一个当时还没提出的需求。**冗余的防护不是免费的,它的代价是延迟支付的。**

### D3 键位只在**持有焦点的面板**内生效 —— 不做全局分发

CM6 的 keymap **只在编辑器持有焦点时触发**;目录树与大纲的处理器挂在各自容器上。因此:

- **三个面板可以各自使用同一批按键而互不冲突**(如 ↑↓ 在三处含义不同,天然分流);
- **不需要任何"我现在在哪个面板"的条件判断** —— 焦点归属就是路由。

这是 `add-tree-keyboard-nav` 那条"**能用结构分流的,别用逻辑分流**"在主题级的复用:**焦点是路由器**。全局键盘分发器会把三个面板的键位耦合成一张必须整体推理的表,而按焦点分流让每个面板只需要对自己负责。

### D4 键位体系:**同族同形**,且**未经真机核验前不写死**

体系形状(**候选,非最终**):

| 动作 | 候选键位 | 理由 / 风险 |
|---|---|---|
| 切换面板 | `Tab` / `Shift+Tab`(**基线,已确定**) | 平台原生,零冲突 |
| 切换面板(便捷层) | 待定 | F6 与 `Mod+数字` 均被占;候选须真机核验 |
| 跳转到定义 | `Mod-B` | 与 JetBrains 一致(肌肉记忆);**未见 Chrome 绑定,待核验** |
| 查找引用 | 待定 | **`Mod-Shift-B` 不可用 —— Windows 上是"显示书签栏"**;需另选 |
| 代码区光标移动 | 方向键 / PageUp/Down / Home/End | 通用,无冲突 |
| 大纲选择 / 定位 | `↑` `↓` / `Enter` | 与目录树同形 |

**两条硬规则**:
1. **每个候选键位在写死前 MUST 进 `docs/manual-verification.md` 并经真机核验** —— 我们已经在 `Ctrl+Shift+O`(书签管理器)上栽过一次,那次是"照文档推断"而非实测。
2. **MUST NOT 因为"IDE 都这么绑"就跳过核验** —— IDE 不在浏览器里跑,它们的键位约定不携带浏览器的占用信息。

### D5 大纲键盘:**复用目录树已验证的模式,而不是复制它的代码**

大纲同样是"虚拟/可变长列表 + 活动项 + Enter 激活"。**模式照搬**:容器唯一可聚焦 + `aria-activedescendant` + 活动项用**稳定标识**(不是行索引)。

**先照搬模式、暂不抽公共组件**:两处的数据模型不同(树是层级 + 路径,大纲是平铺 + 符号),**过早抽象会造出一个两边都不合身的中间层**。若实现后发现两者的键盘逻辑确实近乎一致,再抽 —— **抽象要由重复驱动,不由预感驱动**。

## Risks / Trade-offs

- **[去掉 `editable(false)` 打开了 contentEditable 面]** → D2 的两项验证是**放行条件**,不是可选项;「只读保证」的 Scenario 要扩到输入/粘贴/拖放/IME。
- **[Tab 序里夹着顶栏控件,切面板要按多次]** → 基线可用性可接受,便捷键位作为改善项;**MUST NOT 为了少按两次 Tab 而把顶栏控件移出 Tab 序** —— 那会损害真正依赖 Tab 的用户。
- **[五个部分一起做,面大]** → 它们共享同一套焦点模型,**分开做反而会各自长出一套**;但可按"焦点模型 → 各面板接入 → 键位落地"分阶段验收。
- **[键位与既有 `⌘K` / `⌘⇧O` / `⌘⇧F` 冲突]** → 那三个是全局键位,新键位若也全局就会撞;**D3 的按焦点分流正是避开这一点**的机制 —— 新键位一律绑在面板内,不做全局注册。

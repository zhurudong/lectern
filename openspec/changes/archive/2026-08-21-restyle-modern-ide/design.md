## Context

现有主题机制:`src/styles.css` 已有 `:root` 与 `[data-theme="dark"]` 两套 CSS 变量(`--bg` / `--bg-sidebar` / `--fg` / `--accent` / `--border` …),`src/preview/cmTheme.ts` 提供 CodeMirror 两套主题。**A 方案是替换这些令牌的值 + 增补密度与过渡令牌,不是新建平行体系。**

视觉锚点来自 PM 的真机 mockup(`mockup.mjs` 的 `const A` / `const Alight`),**是方向锚点不是像素级规范** —— 做进真机后由 PM 截图,过渡手感与对比度实测可微调,但方向锁定。

## Goals / Non-Goals

**Goals:** 两套独立调校的完整色板;语法色板随主题成套切换;密度与过渡令牌化;零网络前提下的字体方案。

**Non-Goals:** 不改交互行为与布局结构;不新建主题机制;不做用户自定义主题/配色;不碰代码理解层。

**注释在两套里都是斜体** —— 这是 A 方案的一部分,不是可选装饰。

### D2 等宽字体走系统栈,不内置字体文件(**并纠正一处前提**)

**先纠正**:内置字体文件**不违反零网络** —— 零网络禁的是**引用远程资源**,把 woff2 打进扩展包是本地资源,和内置 SVG 图标同性质。所以这不是红线问题,是**体积与收益的取舍**。(远程 `@font-face` 才是红线,那条绝对不做。)

**结论:用系统等宽栈,不内置。**

```
ui-monospace, "SF Mono", SFMono-Regular, Menlo, Consolas, "Cascadia Mono", "Liberation Mono", monospace
```

- `ui-monospace` 是现代通用族,直接映射到各平台的原生 UI 等宽字体(macOS→SF Mono、Windows→Cascadia/Consolas),**渲染 hinting 由系统调好**,通常优于内嵌字体在非目标平台的表现。
- mockup 里的 `"JetBrains Mono"` **不是任何平台的系统字体**,写在栈里对绝大多数用户是空占位 —— 保留它只会制造"设计稿有、真机没有"的错觉,已从栈中移除。
- 内置的体积账:一款等宽字体 regular+bold 的子集化 woff2 约 100–160 KB,相对当前约 1420 KB 是 **+7~11%**;而它换来的差异,**相对令牌/密度/过渡这三项对"现代 IDE 感"的贡献是次要的**。若后续有人坚持内置,需另行论证并处理字体许可与署名。

界面(非代码)字体保持现状的 `-apple-system, "PingFang SC", sans-serif` 栈 —— CJK 文件名依赖它,不动。

### D3 过渡动画:范围限定,且不与"即时反馈"冲突

只给**状态类属性**加过渡(`background-color`、`box-shadow`、`color`),0.12–0.15s,`ease-out`。

**MUST NOT 给布局属性加过渡**(宽度/高度/位置):侧栏与大纲是拖拽调宽的,给宽度加过渡会让拖拽变成"追着鼠标滑",手感反而更差 —— 这是"加动画治生硬"最容易反噬的地方。

**虚拟滚动的行是复用 DOM 节点的**:滚动时同一个 `.tree-row` 元素会被赋予不同内容,若过渡挂在行背景上,快速滚动可能出现颜色拖影。实现时需验证并在必要时于滚动期间禁用过渡。

### D4 与键盘导航的交接

`add-tree-keyboard-nav` 会引入**活动行焦点环**,其两主题取值当时按现有灰阶定;本 change 落地时 SHALL 把焦点环并入 A 色板一起调,并**重新验证"活动行标识与选中标识可区分"** —— 选中行在 A 方案里有了背景 + 左侧色条,焦点环需要与之明确区分而不是叠成一团。**这条不能靠上一轮的自检结论顺延**(验收结论只对它检查过的那批成立)。

**看过键盘那轮的真机图后补一条具体风险**:当前焦点环与选中态**同属蓝色系**,现在能分开靠的是**形式差异**(环 = 描边、选中 = 填充),不是色相差异。而 A 方案的选中行是**蓝色填充 + 蓝色左侧色条**,再叠一个蓝色描边环,一行上会出现**三个同色系强调元素**。建议方向:**不要再加一种颜色去区分**(那会把问题推给色相拥挤,我们在图标那轮已经吃过),而是让三者**在形式维度上错开** —— 色条(细长实心)、填充(整行底色)、焦点环(描边)本就是三种不同形式,需要确保它们的**粗细与留白**不互相吃掉,必要时让焦点环在选中行上改用内缩描边或提高对比度而非换色。真机自检时**必须看"环 + 色条 + 选中底三者同时出现在同一行"的样子**,而不是分别看。

## Risks / Trade-offs

- **[静态 mockup 无法验证过渡手感]** → 过渡是本 change 的重点交付,验收必须包含 PM 的真机录屏/连拍与用户真人试用,**不能只看静态截图**。
### D5 对 A 方案的两处有据偏离(2026-08-21 实测后裁定)

PM 给的是**方向锚点不是像素规范**,且明确授权"对比度实测可微调"。以下两处按此裁定:

**① 注释色提高对比度(偏离 mockup 值)。** 实测:浅色 `#a0a6b0` on `#fbfcfe` = **2.39:1**,暗色 `#5c6370` on `#13141b` = **3.04:1**。低对比注释是**编辑器**的常见取向,那个取向成立是因为编辑器里你在**写**代码,注释是次要的。**但我们是阅读器** —— 读陌生代码时,注释承载的是原作者的意图,常常是屏幕上**信息密度最高**的文本。**把它做成最难读的元素,与产品目的正好相反。**

裁定:两套主题的注释色 SHALL 达到 **≥ 4.5:1**(正文级 AA)。约束是**保持色相、保持"比代码正文更暗"的层次关系** —— 目标是"次要但清晰",不是"和正文一样重"。改完必须**同时用数值与眼睛复核**(数字达标而观感变得抢眼,同样是失败)。

**② `.ols`(大纲符号色)保持按符号种类分色,不压成 mockup 的单一 fn 蓝。** 种类色本就取自 `--tok-*`,换 A 语法色板后**A 的颜色已自动生效**;而"按种类分色"是图标那轮定下的设计,压成单色等于**用视觉锚点覆盖一条已成立的设计决定**。锚点管方向,不管推翻既有决定。

### 风险与取舍

- **[暗色 `#13141b` 底 + `#c8cdd8` 文本的对比度]** → 实现时按 WCAG 检查正文与次级文本对比度,弱文本(`#5a6172`)仅用于非关键信息(分组标题),不用于正文。
- **[换色板打破既有 E2E 的颜色断言]** → 既有断言里有"首装默认浅色(白底)"等硬编码色值,`#fbfcfe` 不再是 `rgb(255,255,255)`;**这类断言要按新令牌更新,而不是把新色板往旧断言上凑**。补充口径(PM 2026-08-20):更新时**新值 MUST 来自 D1 令牌表这个单一源**,MUST NOT 在断言里手写一个"看起来对"的色值 —— 否则断言与令牌表会各自漂移,而漂移的那一刻两边都还是绿的。
- **[改了皮但局部漏改]** → D1 表里 PM 摘要未列的五处(tab/搜索框/徽标/当前行/大纲符号色)是最可能漏的,验收需逐项对照。

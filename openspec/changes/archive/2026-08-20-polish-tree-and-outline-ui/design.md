## Context

小改动,只碰目录树渲染与面板宽度。现状:`src/tree/Tree.tsx` 的 `fileIcon()` 三行返回 `📂/📁/📄`;`.outline { width: 220px }` 写死;`src/app.tsx` 已有一套完整的分隔条拖拽(`clampWidth` + `mousemove/mouseup` + `localStorage`),只服务左侧。约束见 proposal。

**流程重量按改动重量来**:本文件只记两个会影响实现选型的决定,不做 `add-code-intelligence` 那种规模的论证。

## Goals / Non-Goals

**Goals:** 去 emoji、按语言可辨识、两主题都可读;大纲分隔条与左侧行为一致且共用一份实现。

**Non-Goals:** 不做图标主题/自定义配色;不做文件夹按类型着色;不动 `src/intel/**` 与预览渲染逻辑;不引入任何图标库。

## Decisions

### D1 图标用内联 SVG 字形 + CSS 变量着色(不用图标字体、不用 emoji)

- **字形**:一组内置的极简单色 SVG path(文件、文件夹、图片、二进制,加少量语言专用形状),以内联 `<svg>` 渲染。
  - 不用**图标字体**:字体文件是额外资源、需要 `@font-face`,而且字形随字体渲染差异变化,正是 emoji 现在的问题。
  - 不用 **emoji**:见 spec。
  - 不用**图标主题包**:体积约束。
- **着色**:字形保持单色,颜色由 `data-lang` 对应的 CSS 变量给出。这样**两主题的适配是改变量而不是改图标**,与既有主题机制同构(`:root` / `[data-theme]` 两套变量)。
- **语言归类复用 `identifyByName`**:它已经把扩展名映射到 `{channel, language}`。图标层只做 `language → 色类` 的收敛(如 `c`/`cpp` 同色系),**不新建扩展名表** —— 新建第二张表意味着以后加一种语言要改两处,必然漂移。

### D2 大纲分隔条复用既有拖拽,不写第二份

把 `app.tsx` 里那段拖拽提成一个可复用的钩子/组件,左右两处各传自己的 `storageKey`、`min`、`max` 与方向(左侧向右增宽,大纲向左增宽)。

**MUST NOT 复制一份改方向** —— 这正是本项目已经吃过两次亏的形状(单文件跳转决策、Markdown 行定位):**分叉允许发生在参数层,不允许上浮成两份实现**。方向差异是参数,不是理由。

## Risks / Trade-offs

- **[暗色主题下低饱和色相接近隐形]** → 两套主题各定一组色值(不是给同一组色加透明度),并在 E2E 中断言两主题下图标颜色均非背景色;真机截图人工复核。
- **[色相拥挤]** → **判据:色相间隔只在"字形也相同"时才致命**(实现期量化后得出,2026-08-20)。图标有**字形 + 颜色两个通道**,两族只要字形不同,色相挨得近也分得开;只有**同为 code 字形(`<>`)的族**才必须靠颜色单独扛。据此:`markdown`(text 字形)与 `html/css/xml`(code 字形)同色但不必拆;`csys`(code)与 `asset`(图片框)间隔仅 23° 也不必动;而 `jvm` / `markup` / `js` 三族全是 code 字形,17~18° 的间隔是真问题 —— 已把 java 移到玫红(345°)、JS 系移到偏黄(53°),**code 字形族的最小间隔从 17° 提到 32°**。
  > 推论:**"色相间隔 ≥32°"本身也是一种数字版的假绿** —— 间隔够不等于看得出。量化只用来**定位**问题与**排除**伪问题,最终判断必须放大看眼睛认。
- **[语言数量涨到二十几种后,"一族一色"不再够用]**(PM 2026-08-20)→ 本批加完后需要分色的类型达 20+,**按大类分色系,而不是按语言分色**:系统/后端语言一个色系、脚本/前端一个色系、配置类中性、数据/标记类另一色系;**同色系内部靠字形微差区分**(这正是 D1 那条"两个通道"判据的延伸 —— 颜色负责粗分,字形负责细分)。
  > 视觉自检的判据是 **"扫得快 > 分得清"**:目录树是扫视对象,人眼靠"同族同色系"的粗分定位,不靠精确辨色。**二十种各不相同的颜色,比五个色系更难扫。**
- **["桥色":某个成员脚踩两块,把两个色块连起来]**(2026-08-20,眼睛看出来、数字量不出来)→ 暗色下 go 的 teal 被提亮后偏绿,夹在冷色块(py/c/java)与数据绿块之间,**它不属于任何一块,而是把两块接通了**。修法:暗色单独把 go 往蓝挪(`#2dd4bf` → `#22d3ee`),浅色不动 —— 两套色板本就是独立调的,这正是"两主题各定一组值"该有的用法。代价是暗色下 go 与 py 只隔 10°,但**二者同属冷色块,块内更挤换块间更清,按"扫得快 > 分得清"是该这么换的**。
  > **方法论(比这次修复本身重要)**:当时先量了 go↔data 的两两差距 —— 浅色 33°、暗色 30°,亮度差暗色反而更大,**数字结论是"暗色不比浅色差"**,与眼睛相反。差点据此回绝这个观察。放大看才明白:**问题不在这一对之间,而在"有个成员脚踩两边"**。**两两比对的指标永远量不出桥成员,因为它不落在任何一对里** —— 这是"指标形式的假绿"的一种新形态:指标测的对,但**问题的形状根本不是成对的**。
- **[语言色相太多导致杂乱]** → **分组优先于区分**:同族收敛(C/C++ 一系、JS/TS 一系、YAML/JSON 一系),不追求一语言一色。目录树是**扫视对象**不是辨色测验 —— 十几种各不相同却毫无规律的颜色,**比只有三种颜色更难扫**。
- **[提取拖拽钩子时改坏既有左侧行为]** → 既有"拖拽调整宽度"断言必须仍绿,视为回归门禁。
